# SYSU Charge Watch · 中山大学深圳校区充电桩空位看板

一个**只读**的本地看板，把中山大学深圳校区（SYSU Shenzhen）6 个点位的充电桩实时空闲情况聚合成一页，
并尝试回答一个官方小程序不回答的问题：**「我现在出门，能不能插上？」**

![状态](https://img.shields.io/badge/数据源-青春号TOSUN公开接口-28AC69)
![Python](https://img.shields.io/badge/Python-3.8%2B-blue)
![依赖](https://img.shields.io/badge/第三方依赖-0-brightgreen)

- 🟢 **零依赖**：只用 Python 标准库 + 原生 JS，没有 `pip install`，没有构建步骤
- 🔒 **只读**：不登录、不支付、不下单、不启停充电，丢弃一切个人信息
- ⏱️ **60 秒自动采集**：SQLite 累积时间线，逐步形成"充电通常要多久"的本地统计
- 🏷️ **每个数字都标来源**：真实值 / 推算值 / 置信度，三类分明，不混着说

## 它做什么

### 1. 点位级空闲概览

把平台返回的 48 台电柜、624 个桩位，归并成 **6 个点位**并实时展示：

| 点位 | 电柜 | 桩位 |
|---|---|---|
| 东教学楼 | 12 | 180 |
| 东园宿舍 | 15 | 152 |
| 西园4栋宿舍 | 8 | 120 |
| 医学园 | 5 | 80 |
| 西门右侧 | 7 | 72 |
| 东园食堂地下停车场 | 1 | 20（**长期离线**） |

> 数字来自 2026-11-19 实测。**空闲数会随时间剧烈变化**（数分钟内可跳动 10~20 位），所以看板里的实时值才是准的，别把文档里的快照当现状。

**离线柜不计入忙闲统计**：东园食堂那台柜子失联时，它的 20 个桩位既不算空闲也不算占用，
因此 `ports_total` 会显示 **604**（= 624 − 20）而不是 624。这是有意设计——把离线柜最后一次读到的旧
`chargeable` 当成"现在还有 N 个空位"，会让人白跑一趟。API 里用 `cabinets_all` / `cabinets_offline`
两个字段把这件事说清楚，档位用独立的 `offline`（灰）表示状态未知。

### 2. 五档忙闲配色

| 档位 | 条件 | 颜色 | 标签 |
|---|---|---|---|
| `none` | **在线**且空闲 = 0 | 红 | 已满 |
| `low` | 0 < 空闲率 ≤ 15% | 橙 | 紧张 |
| `mid` | 15% < 空闲率 ≤ 40% | 黄 | 一般 |
| `high` | 空闲率 > 40% | 绿 | 充裕 |
| `offline` | 电柜/点位离线 | 灰 | 状态未知 |

`offline` 与 `none` **必须区分**：`none` 表示"柜子在线，确实一个空位都没有"；`offline` 表示"这台柜子失联，我们什么都不知道"。**把离线显示成"满位"会让人白跑一趟。**

为什么不用参考项目的三档 + 25% 单阈值：本校区实测空闲率跨度 0%~90%，单阈值会让 15% 和 40% 落进同一档，失去区分度。

### 3. 逐电柜下钻

点开任一点位可以看到每台电柜的编号、类型（换电柜/充电柜/充电桩/混合柜）、总位数、空闲数、故障数、在线状态，
以及**可选的**电柜档案（温度、信号强度、固件版本、投运日期、运营商归属）。

**电柜按现场位置编号，而不是按编号字符串排序**（`web/app.js` 的 `geoOrderCabs`）：
- 用每柜真实经纬度做 PCA 求这排桩的**主轴方向**，统一从南/西端开始，标成「第 1 组 … 第 N 组」，
  标题写明方向（如西门右侧「由西南向东北」、东教学楼「由南向北」、医学园「由西北向东南」）。
- 组标签从 `CSTFL10643` 这种难记的编号，换成显眼的「**第 1 组**」徽章 + 小字编号；
  标题栏上方新增**现场位置示意条**——按主轴顺序排的一行小格子，绿/橙/灰点表示该组有空位/占满/故障，
  点格子即切到对应组。**这样"从这一排的左端数第几个有空位"一眼可见，与地图上的视觉顺序完全一致。**
- 编号完全由前端从同一份经纬度算出，与地图共用一份数据源，天然不会两者对不上。

### 4. 区域空位查询（选区域 → 看全部空位 / 最快空出）

第 02 节是一个面向"我现在就去某个区域"的一键查询器：

- **默认折叠**：只显示顶部一排区域按钮（紧凑条），详细的空闲桩位清单收起，避免长列表刷屏；
  点右侧「展开详情 ▾」展开、再点「收起详情 ▴」收起；切换区域不自动展开，展开态跨刷新保留。
- 顶部一排**区域按钮**（按空闲数排序），点一个区域即看它的全部空闲桩位；
- **有空闲时**：按现场位置顺序列出每个组、每组的空闲桩号（"第 3 组 · CSTFL10643 · #5 #6 #9 号桩"），
  并给出该区域空闲总数——**直接告诉你去哪排的哪一格能插**；
- **没有空闲时**：不写"满了"就完事，而是从所有占用桩位里挑出**最快空出的 3–5 个**，
  逐个列出排名 / 组号 / 电柜号 / 物理桩号 / 已充时长 / 预计结束 / 还需多久
  （占用桩位带橙色「实测」标签者为桩端固件真值），并按剩余时间升序排列。
- 页脚明示"「还需」按充电时长历史推算，用户可能提前结束而空出"——**不把推算当承诺**。

离线区域单独提示"状态未知"，不会被误读成"满位"。手机端区域按钮自动折行、零横向溢出。

> 该模块的桌面/手机 6 区域切换与「0 空闲 → 5 条最快空出」两种形态均已逐一验证通过。
> 开发期的自检脚本与交付截图属本机一次性产物，未随仓库分发。

### 5. 电柜地图（真实可缩放底图）

第 03 节是一幅 **Leaflet + 三套可切换底图**的真实可缩放地图（不是静态示意图）：

  切换底图时用反向解算 `gcj02ToWgs84` 把视野中心换回原始坐标，画面不跳。
  > **口径结论（实测）**：平台原始坐标直接落 OSM 与 Esri 卫星影像，西园4栋 8 柜精确落在
  > 「西园6宿舍 / 中国农业银行 / 西园2号楼」真实楼群与路边停车带上，两张独立 WGS84 底图互相印证

  - 离线柜 = 红色 `outLine0`。**这与小程序地图上的灰泡斜排 + 彩泡效果完全一致**，不是自绘彩色实心圆。
- **marker 永远钉在真实地理点，缩放/平移不漂移**：图标以中心对齐经纬度（Leaflet 地理投影，
  无人为像素散开）。坐标相近的几组柜会像小程序那样沿路**自然叠放成斜排**（如西园食堂区一排灰泡），
  而不再被推成虚假的竖列；缩放时图标锚点固定为 40px、位置随地理投影正确变化。

### 6. 时长推算（本项目的核心增量）

官方小程序**没有**"还剩多久空出来"这个功能。本项目有两条链路，按数据可得性自动选择：

#### 链路 A（默认）：用 `chargeable` 的时间线推

- **每 60 秒**采集一次每台电柜的 `chargeable`
- 空闲数**下降** → 记一次新占用（入队，记 `start_at`）
- 空闲数**上升** → 按先入先出取一条记录（出队，算 `duration`）
- 累积成样本后，算中位数 / p25 / p75，估出"已充多久 / 还剩多久"

#### 链路 B（提供 token 后）：直接读桩端固件，精确算结束时刻

这是本项目最重要的一步。桩本身就是"按用户选的目标时长计时、到点断电"的机器，
所以真正决定"什么时候空出来"的不是历史统计，而是**用户当初选了几个小时**。

桩端固件（`queryBoxInfo`）暴露两个关键字段：

| 字段 | 含义 | 实测验证 |
|---|---|---|
| `ct` | 已充电分钟数 | 与 `now − startTime` 偏差中位数 2.5 分钟；两次采样间隔 3.3 分钟时增量 3~4 → 是真计时器 |
| `cs` | 桩端状态码 | 3=充电中（220V/0.8A）、5=手动停止、**6=到点断电**、0=已断电 |

**用户选的目标时长藏在 `cs=6` 里**：到点断电后电池可能还插着，此时 `ct` 就**冻结在目标值上**。
实测 12 个 `cs=6` 端口，`ct` = `[240, 480×11]` —— **12/12 精确命中**小程序的档位
（`["充满", 0.5, 1, 2, 3, 4, 5, 6, 7, 8]` 小时，其中「充满」按 8 小时计费）。对照组 `cs=5`（手动停止）0/9 命中。

于是：

```
结束时刻 = startTime + 目标时长          ← 精确到秒
剩余时长 = 目标时长 − ct                 ← 精确值
```

目标不确定时（充电中、且 `ct < 420`），给出**硬上界**「至多 `480 − ct` 分钟」：
平台最长充电 480 分钟，实测 364 个充电中端口 `ct` 最大 476，无一超 480 —— 这个上界无条件成立。

> 实测样例：`CSTFN4004601` 端口 1，开始 `20:22:15`，已充 268 分钟，
> 目标 480 分钟（概率 80%）→ 预计 **04:22:15** 结束，还剩 212 分钟。

#### 三类「不可用」为什么要分开：`occupied` / `blocked` / `fault`

平台的 `chargeable` 字段容易被字面误解。实测 48 台电柜逐柜比对，**48/48 精确吻合**的公式是：

```
chargeable == count(infraed == 0 AND status == 1)
```

也就是说 `chargeable` 的语义是「**红外没检测到东西（端口空着）且硬件正常**的端口数」，
而不是「没在充电的端口数」。同理 `errorCell == count(status != 1)`。

所以平台本身**没有 bug** —— 它一直没把「电池还插着」的端口算进空闲。
但只看 `chargeable` 这一个数字，你无法区分「这个端口空着」和「这个端口为什么不能用」。
本项目把它拆成四类，四类之和恒等于 `capacity`，且 `free` 恒等于平台的 `chargeable`：

| 分类 | 判定 | 含义 | 用户该怎么做 |
|---|---|---|---|
| `free` | `status==1 且 infraed==0` | 真的空着，插进去就能充 | 直接用 |
| `occupied` | `infraed==1 且 chargerStatus ∈ {1,2,3}` | 别人正在充 | 看剩余时间 |
| `blocked` | `infraed==1` 但未充电 | 电池还插在柜里（充满未取 / 到点断电未取） | 插不进去，等 |
| `fault` | `status != 1` | 硬件异常 | 换一个 |

`blocked` 是平台不给、小程序也不展示的一类。实测全量稳定 55~61 个端口处于这个状态，
所以本项目在**五个层级**同时暴露它：

| 层级 | 呈现 |
|---|---|
| 全场概览 | 「空闲桩位」= 平台 `chargeable`（与小程序地图一致），另起一项「断电未取走 N 个」 |
| 点位卡片 | 「断电未取走 N 个」（橙色加粗） |
| 电柜组标签 | `断电 N` 角标，不用点进去就知道这组有几个插不进去 |
| 桩位网格 | 虚线橙框 + 「已断电」字样（区别于实心橙的「被占用」） |
| 桩位详情 | 状态「已断电未取走」+ 目标时长 + 剩余「即将空出」+ 电压 0.0V / 电流 0.000A |

> **一致性保证**：`free + occupied + blocked + fault == capacity`，且 `free == chargeable`。
> 实测 48 台电柜全部成立（校验脚本见「验证」一节），这是「地图与点位明细数字永远一致」的前提。

**链路 B 的 `ct` 与结束时刻是桩端真值，不是推算**；但目标时长在 `cs=3 且 ct<420` 时仍需按档位分布推断，
所以「预计剩余」在那种情况下仍标为推断值。链路 A 完全是指标推算。
详见 [数据是怎么来的](#数据是怎么来的) 与 [已知限制](#已知限制)。

### 7. 每日桩位趋势（看需求会怎么变）

第 06 节把数据库里累积的每次采集摊成一条曲线，回答"**这个区域一天里什么时候最挤**"：

- **先选日期**：顶部一行默认折叠成「选择日期｜今天 ▾」，点开是最近 **7 个自然日**
  （`今天` / `昨天` / `11/18` …）。没有采样的日子显示为虚线框 + `无数据`，
  今天的按钮额外标「进行中」，因为这一天还没走完；
- **再选区域**：`全校区` + 6 个在线点位，按桩位数降序（食堂长期离线故不出现）；
- **再选曲线**：`可用桩位`（绿）/ `占用桩位`（橙）两个按钮互斥切换，默认看可用——
  两条曲线是同一批数据的两个视角，**同一时刻满足 `可用 + 占用 + 故障 ≈ 总桩位`**，所以只显示一条不会误读；
- **横轴恒定 0:00–23:59**：坐标轴是按「当天第几分钟」映射的固定轴，跟数据多少无关。
  所以今天才采到 20:50 时，曲线只画到右边一点就停住，左边对齐 0:00、右边留着空白，
  **一眼就能看出"这一天采了多久"**，而不是把半天数据拉伸满屏；
- **每 10 分钟一个采样点**（整天 → 144 点）。原始库是每 60 秒一条、48 柜 × 1440 轮 ≈ 8.6 万行，
  直接画会把曲线糊成噪声；分桶时**每个电柜在每个 10 分钟桶里只取最后一条**，
  再对在线电柜求和，既保留真实波动又不会因采样时刻不齐而虚高；
- **只有在线电柜参与求和**：某个柜离线时它的桩位从该时间点的分母里消失，
  所以曲线在故障时段会有台阶，这是真实状态而不是数据缺失；
- **断档就断开，不画假线**：服务停过几小时的话，相邻两个采样点会隔很远。
  程序把间隔超过 **20 分钟** 的地方判定为"这段时间没在采"，把折线**断开成两段**
  并在断点画一条虚线柱——否则一条凭空直连的斜线会让人误以为那段时间一直在正常采集；
- Y 轴 5 档自适应缩放，最右端一个橙点 + 数字标出**最新值**，
  图脚给出 `日期 · 已采集/覆盖 起→止 · 均值 · 横轴固定 0:00–23:59`。

> 为什么这条曲线可信：它不是估算，是**本项目自己按 60 秒一轮采下来的历史**。
> 平台只提供"此刻的快照"，不提供任何历史查询接口——这也是本项目必须常驻运行的原因。
> 换句话说，**这个功能的价值随时间增长**：跑得越久，能回看的日子越多（当前上限 31 天）。

> 这条曲线的桌面 / 手机 / mock 三态（日期栏折叠展开、横轴严格 00:00→23:59、切日期、切区域、
> 切曲线、断档段数 = 虚线柱数 + 1、零 JS 错误，共 138+ 项）均已逐一验证通过。

## 它不做什么

| 不做 | 说明 |
|---|---|
| ❌ 扫码 / 自动登录 | 平台没有对外可用的登录入口，不伪造登录；可选由**你手动提供**自己抓包得到的 token（见下） |
| ❌ 下单 / 支付 | 无订单、无支付、无钱包 |
| ❌ 启停充电 / 开柜门 | 不向平台发任何会改变状态的请求 |
| ❌ 采集个人信息 | 接口返回的 `mobile` 字段被**直接丢弃**，不入库、不进 API、不上前端 |
| ❌ 高频轮询 | 60 秒一轮，与平台自身缓存和小程序刷新节奏同量级 |

### 可选：逐桩位真实数据（手动 token）

青春号小程序的逐桩位接口（`getCaboxListByCabinetNo`）需要登录 token **和手机号两个参数**（缺一不可）。
**平台没有扫码/验证码登录给我们调用**，所以本项目不伪造登录；但如果你愿意，可以自己在微信里登录一次小程序，
按 [抓包获取 Token 指南](docs/抓包获取Token指南.md) 把请求头里的 `token` 和请求参数里的 `mobile` 一起截下来，
贴到看板顶部的「登录凭证」面板（两个输入框）。之后：

- 每个占用桩位的**已充时长**优先取**桩端固件 `ct`**（精确，与 `startTime` 差 <3 分钟），退而用平台 `endTime − startTime`（实测 `chargeTime` 字段恒为 `null`，不可用），带橙色「实测」标签与电量/电压/电流信息；
- 端口四分类走统一口径 `tosun_client.classify_port()`（`free`/`occupied`/`blocked`/`fault`），保证 `free` 恒等于平台 `chargeable`、四类之和恒等于 `capacity` —— 这是地图、概览、点位明细三处数字永远一致的前提（见上节）；
- **目标时长**在 `cs=6`（到点断电）或 `ct ≥ 420` 时可确定，此时「预计结束」是**精确时刻**、「预计剩余」是精确值；否则给出「至多 `480 − ct` 分钟」的上界并标注推断概率；
- 逐桩位数据由后台线程拉取（并发 16，实测 48 柜约 **17 秒**），且**由采集循环驱动**（每轮采集完成后立即触发，限频 55 秒 < 轮询 60 秒），保证明细与地图同步更新、不出现跨轮延迟；首屏先用推算数据秒开，真实数据到位后自动切换，不阻塞页面；
- 固件采样每轮 180 个端口（并发 12，约 2 分钟），带轮转游标与两级缓存（110 秒判重采 / 900 秒判可展示），异常端口优先采；
- token 失效、留空或拉取失败时，页面**自动退回公开推算模式**，不会中断；
- token 只保存在本机 `data/config.json`，只用于只读状态查询，不写浏览器存储、不进网址、不出现在任何 API 响应里（只回后四位掩码）。

不使用这个功能，看板的全部核心功能照常可用。

横轴是**固定时间轴**，当天还没采完的部分留白，右端橙点标最新值。见 [它做什么 §7](#7-每日桩位趋势看需求会怎么变)。

### 三个可信度标记

看板上的数字分三档，**不要混读**：

| 标记 | 含义 |
|---|---|
| 直接显示的数字 | 平台实时给的（如空闲数、总数、故障数） |
| 橙色「实测」标签 | 桩端固件读到的真值（`ct` / 电压 / 电流 / 电量 / `cs`），提供 token 后才有 |
| 带"约 / 估计 / 至多 / 推断 N%"的数字 | 本项目推算的（如公开模式的已充时长、目标时长未知时的剩余） |
| 灰色或 `—` | 数据不足，**不给猜测**（如冷启动期的剩余时长、离线柜的状态） |

冷启动时你会看到「数据积累中，约需 1–2 天形成可靠估计」。这是诚实的表现，不是缺陷。

### 怎么读"预计还有多久"

点位卡片上的 `forecast` 有两个数字最容易误读：

- `expected_free_30m: 0` —— 未来 30 分钟内**预计有 0 个桩位空出**（有样本，确实判断为 0）
- `expected_free_30m: null` —— **没有样本，拒绝预测**（不是 0）

同理 `next_free_in_minutes: null` 表示"不知道"，而不是"立刻"。UI 对 `null` 必须显示 `—` 而不是 `0`。

### 数据流（一次采集）

```
poller 线程每 60 秒醒来
  → tosun_client.list_around(6 个中心点, scan_distance_km=3)
      → 6 个点并发 POST，各自返回 ≤100 条，按 cabinetNo 去重保留最近
  → server.is_campus(location) 名称锚定过滤 → 48 台校园柜
  → 组装 rows：chargeable / capacity / fault(=errorCell) / online / location / lng / lat
  → tracker.record_poll(rows)
      → 比对上次 chargeable → 入队 / 出队 / 写 charge_session
      → 补 backlog、写 cabinet_sample、写 poll_log、清理 30 天前数据
  → tracker.prune_impossible()  删掉超过 8 小时的僵尸占用
  → 更新内存 LAST_SNAPSHOT（供 /api/state 立即返回，不阻塞 HTTP）
```

有 token 时，另有两条**异步**支线（都不阻塞上面这条主链）：

```
明细支线（采集驱动：每轮采集后立即触发，限频 55 秒 < 轮询 60 秒；后台线程，并发 16 约 17 秒）
  → tosun_client.cabinet_details(48 柜, token, mobile, max_workers=16)
      → POST /v1/user/getCaboxListByCabinetNo（逐柜）
      → 拿到每个桩位的 startTime / chargerStatus / chargeOrderNo / infraed
  → 写入 AUTH_STATE["details"]
  → 触发固件采样支线

固件支线（每轮最多 180 个端口，约 2 分钟，异常端口优先，后台线程）
  → 选端口：平台判占用 + 平台判空闲但 chargerStatus ∉ {0,1,7}（后者才能发现 blocked 端口）
  → box_sampler.get_many(pairs, token, mobile, budget=180)   并发 12，轮转游标
      → POST /v1/user/queryBoxInfo（必带 port）→ cs / ct / 电压 / 电流
  → target_model.observe(boxes)   学习 cs=6 冻结的 ct → 目标档位分布
  → _build_real_occupancy 用固件读数组装：
      elapsed   = ct（精确）
      target    = cs=6 ? ct : 档位反推
      remaining = target − ct
      end_at    = startTime + target
```

**首屏策略**：`/api/state` 从不等待上面两条支线。第一次请求返回公开推算数据，
明细与固件陆续到位后，下一次 60 秒轮询自动切到精确数据，页面不需要刷新。

## 数据是怎么来的

### 第一层：平台给的（实测）

主数据来自一个**免登录**接口：

```
POST https://cloud.tosunelectric.com/v1/user/getCabinetListAround
Content-Type: application/x-www-form-urlencoded;charset=UTF-8

longitude=113.9457&latitude=22.8036&distance=3&batteryTypes=&mobile=&source=CSTF
```

返回每台电柜的一条记录，关键字段：

| 字段 | 含义 | 本项目怎么用 |
|---|---|---|
| `cabinetNo` | 电柜编号 | 主键 |
| `location` | 点位名 | 归并到 6 个点位 |
| `capacity` | 总桩位（`"10"` 或 `"14,6"`） | 逗号分段求和 |
| `chargeable` | **空闲数** | 核心指标 + 时间线推算的原料 |
| `errorCell` | 异常格数（**推断**为故障数） | 展示为"故障" |
| `online` | `1` 在线 / `0` 离线 | 离线柜排除出忙闲统计 |
| `cabinetType` | `1 换电柜 / 2 充电柜 / 3 充电桩 / 4 汽车桩 / 5 混合柜` | 类型标签 |
| `exchangeable` | 可换电电池数 | 换电柜展示 |
| `distance` | 距中心点（**字符串**，单位 km） | 排序、去重择近 |

**三个必须记住的平台特性**（都是实测踩出来的）：

1. **必须 form 编码**。JSON body 会被拒，返回 `{"code":1,"msg":"getCabinetListAround error"}`。
2. **`distance` 单位是公里，不是米**，且单次返回**硬上限 100 条、无分页**。所以用 6 个中心点扫描再按 `cabinetNo` 去重。
3. **`capacity` 是字符串**，混合柜是逗号串（`"14,6"` = 14 个柜位 + 6 个桩位）。

### 第二层：平台不给的（这是最关键的边界）

| 能力 | 接口 | 免登录？ |
|---|---|---|
| 每台电柜的空闲**数** | `getCabinetListAround` | ✅ 是 |
| 每个桩位的**状态**（哪号空、充了多久） | `getCaboxListByCabinetNo` | ❌ **需要登录 token + mobile** |
| 桩端固件**计时器**（`ct` / `cs`） | `queryBoxInfo`（必带 `port`） | ❌ **需要登录 token + mobile** |
| 用户当初选的**目标时长** | 无接口 | ❌ **平台不回吐**（见下） |

已系统验证：用 `"1"` / `"test"` / UUID / 32 位 hex 等伪造 token 逐一尝试，**全部失败**。
因此本项目**不尝试绕过**。

**目标时长是平台明确不回吐的字段**，三条路都堵死：

| 尝试 | 结果 |
|---|---|
| `cabox.chargeTime` | 136 个占用端口全为 `null` 或 `0.0`，无一有值 |
| `get_charge_order_detail`（订单详情） | 所有参数组合均返回 `{"code":1,"msg":"参数缺失"}`；该接口在小程序里只出现在 API 表，从未被调用 |
| 固件 `im` 字段 | 恒为 `000000000000000`，与目标时长无关 |

**唯一突破口是固件 `cs=6` 时冻结的 `ct`**（见 [它做什么 §6](#6-时长推算本项目的核心增量)）。

### 第三层：推算（`tracker.py`）

```
每 60 秒：
  Δ = 新的 chargeable − 上次的 chargeable

  Δ < 0（空闲变少）→ 新增 |Δ| 个占用，start_at = now，入队
  Δ > 0（空闲变多）→ 从队头按 FIFO 取 Δ 个，duration = now − start_at → 记为一条完整样本
  Δ = 0           → 只更新时间戳
```

**五个设计要点**（每一个都对应一个真实会踩的坑）：

| 设计 | 解决的问题 |
|---|---|
| **只在两次都在线时才算差** | 离线/恢复会造成 `chargeable` 假跳变，不能污染时长分布 |
| **首次运行的已有占用标为 `backlog`** | 程序启动时柜子上已经有人（实测首轮就有 430+ 个），真实起点未知。这类记录的"已充"只能当**下界**、"剩余"只能当**上界**，且**释放时不参与中位数统计** |
| **样本少于 8 条时收缩到 180 分钟先验** | 贝叶斯式收缩：`shrunk = (raw×n + 180×20) / (n+20)`。样本少时被先验拉住，避免用 2 条"插上就拔"的噪声算出荒谬的中位时长 |
| **剩余时长用条件生存估计** | 不用朴素的 `中位数 − 已充`（已充超过中位数后会给出 0，错误宣称"马上空出"）。改用历史样本中所有 `> elapsed` 的观测求中位数；不足 8 条时退回 `PRIOR × exp(-elapsed / PRIOR)` 指数先验 |
| **有效时长限定 10~480 分钟** | 短于 10 分钟（拔插抖动/误插）和长于 8 小时（可能没拔）的样本都剔除 |

**置信度分级**（`duration_stats`）：

| 样本数 | `confidence` | UI 表现 |
|---|---|---|
| 0 | `none` | 不显示时长，提示"数据积累中" |
| 1–7 | `low` | 显示但标注"样本少" |
| 8–29 | `medium` | 正常显示 |
| ≥ 30 | `high` | 正常显示 |

**冷启动的诚实做法**：`samples = 0` 时，`median_minutes` 返回先验值 180 但 `observed_median_minutes = null`、
`confidence = "none"`、`p25/p75 = null`、`forecast` 里各预测字段为 `null`（**不是 0**）。
API 与 UI 都明确区分"有先验"和"有观测"——**不能因为看到 180 这个数字就当成真实观测**。

## 配置

配置文件 `data/config.json`（不存在时使用内置默认值，改配置时自动创建）：

```json
{ "poll_interval": 60, "token": "", "scan_distance_km": 3 }
```

| 键 | 默认 | 范围 | 说明 |
|---|---|---|---|
| `poll_interval` | `60` | 20 ~ 600 | 采集间隔（秒） |
| `scan_distance_km` | `3` | 0.5 ~ 50 | 扫描半径，**单位是公里**（平台 `distance` 参数就是 km，会截断到 100 条硬上限） |
| `token` | `""` | — | 可选。留空即 `public` 模式；填入后解锁逐桩位真实数据（见[抓包指南](docs/抓包获取Token指南.md)）。`/api/config` 返回时只给 `token_configured` 与后四位打码预览，**绝不明文回传** |
| `mobile` | `""` | — | 逐桩位接口的必传手机号，与 token 一起抓包获取；只回打码预览（如 `177****1790`） |

运行时改配置：

```bash
curl -X POST http://127.0.0.1:8787/api/config \
  -H "content-type: application/json" \
  -d '{"poll_interval": 90}'
```

手动触发一次采集（限频 20 秒）：

```bash
curl -X POST http://127.0.0.1:8787/api/poll
# 太快会返回 429 {"ok":false,"reason":"rate_limited","retry_in_seconds":12}
```

## 已知限制

### 1. 逐桩位状态：公开模式为推算，提供凭证后为实测

平台把逐桩位数据锁在登录之后。默认公开模式下本项目**不伪造**物理桩位，而是构造**逻辑桩位**并在每个响应里显式标注：

```json
{
  "estimated": true,
  "note": "桩位号为逻辑编号，按空闲数变化顺序推定，非真实物理编号"
}
```

`port` 字段的数字**不代表第几号柜格**。UI 上写"1 个占用中"，不写"3 号桩位占用"。

### 2. 时长：公开模式是推算，凭证模式大部分是精确值

| 模式 | 已充时长 | 剩余时长 |
|---|---|---|
| 公开（无 token） | 按 `chargeable` 时间线 FIFO 推算 | 历史统计的条件生存估计，**是推算** |
| 凭证 + 采到固件 | 桩端 `ct`，**精确**（差 <3 分钟） | 目标已知 → **精确值**；目标未知 → 「至多 `480 − ct`」硬上界 |
| 凭证 + 未采到固件 | `endTime − startTime` | 历史统计推算 |

仍存在的两个系统性误差源：

| 误差源 | 说明 | 缓解 |
|---|---|---|
| **目标时长推断可能错** | `cs=3` 且 `ct < 420` 时，目标由档位分布推断（默认「充满」= 8h 概率最高）。若用户其实选了 4h，剩余会被高估 | 给出推断概率与候选档位；同时给「至多 `480 − ct`」硬上界；`ct ≥ 420` 时自动转精确 |
| **用户随时可能手动结束** | `cs=5` 占实测 3.7%，`ct` 为任意值，无法反推目标 | 无法消除，写进 UI 说明 |
| **公开模式 FIFO 是假设** | `chargeable` 上升时不知道是哪个桩位空了，只能按先入先出取队头 | 提供 token 后走固件链路，此问题消失 |
| **公开模式起点下界** | 程序首次运行时柜子上已有人，真实起点未知 | 标为 `backlog`，`elapsed` 当下界、`remaining` 当上界，且不参与中位数统计 |

### 3. 冷启动没有数据

第一天的看板只有实时空闲数，**没有时长**。需要 1~2 天积累才有 `low` 以上置信度。
UI 会明确显示「数据积累中，约需 1–2 天形成可靠估计」。

### 4. 平台字段语义是推断的

`errorCell`（异常格数）的"故障桩位"语义是**推断**，依据是实测恒满足 `chargeable + errorCell <= capacity`
且从不超过 `capacity`。**平台文档没有定义它，小程序前端也从未使用它**（全部 JS 中零命中）。
本项目按推断使用，并在 API 与 UI 中一律标注。

### 5. 离线柜的桩位不计入忙闲

离线电柜上报的 `chargeable` 不可信，因此它的桩位**既不算空闲也不算占用**，也不计入 `ports_total`。
实测中 `ports_total` 为 **604**（= 624 − 20，那台离线柜的 20 个桩位），
而 `cabinets_all = 48` / `cabinets_offline = 1` 保留了完整口径。

这是有意设计，不是算错。**把离线柜显示成"已满"或"还有 N 个空位"都会误导人。**
档位用独立的 `offline`（灰）与 `none`（红，在线且真满）区分。

### 6. 只有 6 个点位、48 台柜

点位归并表写在 `data/sites.json` 里，覆盖中山大学深圳校区的实测数据。
换校区需要改这个文件（`raw_locations` / `center` / `scan_centers` / `location_match`）。

### 7. 单机单实例

服务是单进程设计，数据存在本地 SQLite。多开会导致数据库竞争（WAL 能扛但没意义）。

## 合规声明

### 数据来源

- **公开模式（默认）**：数据来自青春号 TOSUN 平台**免登录**的附近电柜查询接口
  （`/v1/user/getCabinetListAround`），以及两个同样免登录的增强接口
  （`/v1/user/getCabinetInfoByCabinetNo` 电柜档案、`/v1/user/getChargePerHour` 定价）。
- **可选实测模式**：由用户**自行提供**自己抓包得到的 `token` + `mobile`，本项目仅代其调用
  只读的逐桩位查询（`getCaboxListByCabinetNo`）。不破解、不伪造、不绕过登录。

### 只读承诺

本项目**仅做只读聚合与展示**：

- 不涉及**登录**、账户、支付、订单或启停充电
- 不向平台发送任何会改变状态的请求
- 用户提供的 `token` / `mobile` 只保存在本机 `data/config.json`，仅用于只读查询；
  响应中一律打码，不写浏览器存储、不进网址

### 关于"推算"与"实测"

- **默认公开模式**的「已充时长 / 剩余时长」为基于空闲数变化的历史推算，非平台官方数据，仅供参考。
  官方小程序本身也没有"还剩多久"这一功能；这些估计由本地采样时间线推导，可能偏差较大，
  看板上每个推算值都带置信度标注——**请勿当作可依此决策的精确信息**。
- **提供凭证后**，「已充时长」= 桩端固件 `ct`（**真值**，与 `startTime` 差 <3 分钟，标橙色「实测」）；
  「预计结束 / 预计剩余」在目标时长可确定时（`cs=6` 到点断电，或 `ct ≥ 420`）是**精确值**，
  否则是「至多 `480 − ct` 分钟」的上界并标注推断概率。
- 目标时长来自桩端断电时冻结的 `ct`，是平台**不主动提供**但桩本身真实记录的信息；
  它反映的是用户当初选了几小时，**不保证用户不会提前手动结束**。
