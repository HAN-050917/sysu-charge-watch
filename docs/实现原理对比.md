# 实现原理对比

三个项目、同一件事（"校园充电桩空闲情况可视化"）、三种不同的数据可得性。

| | 参考项目 | 平台现用 | 本项目 |
|---|---|---|---|
| 名称 | **STU Charge Watch**（汕大充电） | **青春号 TOSUN**（长盛泰富运营） | **SYSU Charge Watch** |
| 学校 | 汕头大学（STU） | 中山大学深圳校区（现用） | 中山大学深圳校区 |
| 角色 | 第三方只读看板 | 官方运营小程序（用户下单用） | 第三方只读看板 |
| 数据源 | `https://wx.isfdz.com/` | `https://cloud.tosunelectric.com/` | 同左（复用平台公开接口） |
| 技术栈 | Python 3.10+ 标准库 + 原生 JS + Android 客户端 | 微信小程序（UniApp/Vue2 编译产物） | Python 3 标准库 + 原生 JS |

> **一处名称更正**：参考项目的标题是「汕大充电 · STU Charge Watch」，其中 STU = **汕头大学**（Shantou University），不是深圳大学。本文全篇按源码事实写「汕大」。

---

## 1. 先看一句话结论

| 项目 | 它解决的问题 | 它拿不到什么 |
|---|---|---|
| 汕大参考项目 | "**哪台设备现在有空位**"——做到逐桩位 | 时长信息（平台不给） |
| 青春号小程序 | "**我要立刻下单充电**"——做到逐桩位 + 订单 | 不给第三方用（全部需登录）；也不告诉用户"还剩多久" |
| 本项目 | "**现在去哪充、还要等多久**"——点位级 + 逐桩位 + 精确结束时刻 | 无 token 时只有电柜级汇总；目标时长需反推 |

三者的差别**首先不是技术能力差别，是数据权限差别**。这是本文最需要读懂的一点。

但本项目多走了一步：**在用户自愿提供自己 token 的前提下，把数据权限之外的那部分能力补上了**——
桩端固件的 `ct`（已充分钟数）和 `cs`（到点断电）是平台不主动展示、但物理上真实存在的信息。
这使「结束时刻」从统计估计变成**精确到秒的计算**（见 §2.4.1）。

## 2. 核心对比表（三列）

### 2.1 数据获取

### 2.2 空闲状态判定

| 维度 | 汕大参考项目 | 青春号 TOSUN | 本项目 |
|---|---|---|---|
| 空闲的原始定义 | `state == 1`（逐桩位状态码） | `chargeable`（电柜级可充数） | `chargeable` |
| 状态码表 | `{0:粘连故障, 1:空闲, 2:占用, 3:短路保护, 4:设备暂停, 5:高温保护, 6:过流保护, 7:过压保护, 8:欠压保护}` | `chargerStatus`：`{0/7:待机, 1/3:充电中, 2:预充, 5:充电停止, 6:未充满}`<br>占用判定另用 `chargeOrderNo` 前缀 `CD` | **不用状态码**（拿不到） |
| 占用判定 | `state == 2` | `isCaboxOccupied = chargeOrderNo.substring(0,2) === "CD"` | 由 `chargeable` **下降**推断 |
| 释放判定 | `state == 1` 且此前为 `2` | 订单结束（`endStatus`） | 由 `chargeable` **上升**推断 |
| 故障判定 | `state ∉ {1,2}` 即"其它" | 有独立 `status` 字段（`status != 1` 走故障分支） | `errorCell`（**【推断】**语义） |
| 双重校验 | 无（单一 `state`） | **有**：`infraed`（红外）与 `chargeOrderNo`（订单）相互印证 | 无（只有汇总数） |
| 逐桩位可见 | ✅ 完整 `{num, state, label}` | ✅ 完整（但**需登录**） | ❌ 构造**逻辑桩位** |

> **最关键的一行**：汕大和青春号都能做到"第 3 号桩位空闲"，本项目只能做到"这台柜现在还有 2 个空位"。前者靠"逐桩位状态码"，后者靠"电柜级计数"。这不是实现选择，是接口权限。

### 2.3 桩位编号的可靠性

| 维度 | 汕大参考项目 | 青春号 TOSUN | 本项目 |
|---|---|---|---|
| 编号来源 | 平台返回的真实 `num`（物理编号） | 真实 `port` / `caboxId` | **逻辑编号**，按 `chargeable` 变化顺序推定 |
| 是否可用于"去 3 号桩" | ✅ 可以 | ✅ 可以 | ❌ **不可以** |
| 对用户的表述 | "03 号插座，空闲" | "3 号仓，可使用" | "逻辑桩位 #1，估计还剩 42 分钟" |
| 前端是否标注 | 按 `num` 排序，`aria-label` 带编号 | 逐格展示 `caboxId` | 每个桩位带 `basis` 字段区分 |
| 校验手段 | 校验 `1 <= num <= 100` 且不重复 | 无（直接信任服务端） | `basis ∈ {observed, backlog, derived}` |

**这条差异必须让用户看见**。本项目在 API 里强制带：

```json
{
  "estimated": true,
  "note": "桩位号为逻辑编号，按空闲数变化顺序推定，非真实物理编号",
  "ports": [{ "port": 1, "state": "occupied", "basis": "backlog", "elapsed_is_lower_bound": true }]
}
```

`port` 字段的数字**不代表第几号柜格**，只是一个序号。UI 上不能写"3 号"，只能写"1 个占用中"。

### 2.4 时长信息（差异最大的一块）

| 维度 | 汕大参考项目 | 青春号 TOSUN | 本项目 |
|---|---|---|---|
| 能不能拿到真实已充时长 | ❌ 完全拿不到 | ✅ 能（登录后读桩端固件 `ct`） | ✅ 有 token 时能（同样读 `ct`） |
| 平台"看起来能给"的时长字段 | 无 | `cabox.chargeTime`（实测恒 `null`）<br>`cabox.endTime`（实测 = `updateTime`，不是结束时间）<br>`chargeOrderDetail.chargeChargeTime`（需登录，且查不到别人的） | 三个全部实测为废，已排除 |
| **真正可用的时长数据源** | 无 | **桩端固件 `queryBoxInfo` 的 `ct`**（已充分钟数） | 同左（`box_sampler.py`） |
| 用户选的目标时长 | 无 | 平台不回吐；`cs=6` 时 `ct` 冻结在目标值上 | 反推（`target_model.py`），`cs=6` 精确、`ct≥420` 精确 |
| 小程序是否有"还剩多久" | — | ❌ **没有**（全量检索零命中） | ✅ 有（目标确定时精确到秒） |
| 本项目怎么算（无 token） | — | — | 每 60 秒采 `chargeable`，Δ<0 入队，Δ>0 FIFO 出队记录 `duration` |
| 本项目怎么算（有 token） | — | — | 读固件 `ct` → 已充精确；反推目标 → `结束 = startTime + 目标`，`剩余 = 目标 − ct` |
| 统计量 | — | — | 中位数 / p25 / p75，贝叶斯收缩到 180 分钟先验（仅无 token 时用） |
| 冷启动表现 | — | — | 无 token：`confidence: "none"`，各时长字段 `null`<br>有 token：首个固件采样轮（约 30 秒）后即有精确值 |
| 可信度标注 | — | — | `confidence ∈ {none, low, medium, high}`（无 token）<br>`estimate_basis ∈ {firmware_frozen, slot_constraint, prior, firmware_ct, conditional_median}`（全模式） |

**这张表里最反直觉的两格**：

1. 汕大参考项目**没有**做时长，官方小程序**也没有**做"还剩多久"。所以本项目做的是**两边都没有的功能**——这既是价值，也意味着**没有任何官方界面可以对照验证**。因此它必须自带可信度标注。
2. 平台**看起来**给了三个时长字段（`chargeTime` / `endTime` / `chargeChargeTime`），实测**全是废的**；真正的计时器藏在没人会去看的桩端固件接口里。**先看字段名再下结论会踩坑，必须逐字段实测。**

### 2.4.1 目标时长反推：为什么 `cs=6` 是关键

| `cs`（桩端状态） | 数量（624 端口全扫） | `ct` 值特征 | 命中时长档位 |
|---|---|---|---|
| `3` 充电中 | 364 | 连续分布，max 476 | 15%（±5min 内，符合随机预期） |
| `6` **到点断电** | 12 | `[240, 480×11]` | **12/12 = 100%** |
| `5` 手动停止 | 14 | `[1, 87, 141, 165, 218, 239, 257, 272, 476, ...]` | **0/14 = 0%** |
| `0` 已断电（陈旧） | 106 | 全 0，或 `startTime` 在 2023/2024 | 不适用 |

`cs=5` 的 0/14 是**最关键的排除实验**：如果 `ct` 只是"随手一个数"，`cs=6` 不可能 12/12 精确落在档位上。
**所以 `cs=6` 的 `ct` 就是用户当初选的目标时长（分钟），冻结在那里不会归零。**

由此：
```
目标时长 = cs==6 ? ct : 由档位分布反推（ct≥420 时只剩 480，必然精确）
结束时刻 = startTime + 目标时长     ← 精确到秒
剩余时长 = 目标时长 − ct            ← 精确值
```

这条链路是汕大参考项目**结构上不可能有**的：它连逐桩位接口都没有。

## 3. 三者各自如何处理"空闲"这件事（原理层）

### 3.1 汕大参考项目：一条真值链

```
getEquipType(code)  →  equip_type
    ↓
equip_type ∈ {2,6,8,10,11,12,13,14}  →  afterProtocol
equip_type ∈ {1,4,7,3,5,9}          →  beforeProtocol
    ↓
getLineInfo({code, parentCode: ""})  →  [{num: 1, state: 1}, {num: 2, state: 2}, ...]
    ↓
state == 1 → 空闲   state == 2 → 占用   state ∉ {1,2} → 其它/故障
    ↓
counts = {total: N, free: Σ(state==1), busy: Σ(state==2), other: 其余}
```

**它的"空闲"是平台直接告诉它的**——`state == 1` 就是空闲。没有任何推算。这是最理想的情况。

代价是：需要抓 `app_id`/`app_secret` 算签名（凭据只能驻内存，6 小时缓存），且必须预置设备清单（`catalog.json` 里 14 个 id），没法"自动发现附近设备"。

### 3.2 青春号 TOSUN：两层真值，第二层锁住

```
getCabinetListAround(lng, lat, distance=50km)
    ↓
每条记录：{cabinetNo, capacity: "14,6", chargeable: 3, errorCell: 1, online: 1, ...}
    ↓
空闲数 = chargeable（电柜级，公开）          ← 第一层：免登录
    ↓
点击电柜 → checkCabinetInfo({cabinetNo, mobile})
    ↓
caboxs: [{caboxId, port, chargeOrderNo: "CD2026...", infraed: 1,
          chargerStatus: 1, status: 1, percentage: 62, chargeTime: 47, ...}]
    ↓
占用 = chargeOrderNo 以 "CD" 开头（且 infraed == 1 时才算）
故障 = status != 1
空闲 = infraed == 0 && status == 1
                                             ← 第二层：需登录 token
```

**它的"空闲"也是平台直接给的**（第一层），但只给到"这台柜还有几个空位"。要问"哪几个位置空着"，就得进第二层。

第二层的判定很有意思——它**不用一个 `occupied` 布尔字段**，而是：

```js
isCaboxOccupied: function (n) {
  return !(!n.chargeOrderNo || "CD" != n.chargeOrderNo.substring(0, 2));
}
```

即"这个柜盒上挂着一条 `CD` 开头的订单" = 占用。同时模板里 `infraed == 1`（红外检测到有东西）也参与判定。**红外 + 订单双证据**，比单一状态位更可靠。

### 3.3 本项目：从计数反推事件

```
每 60 秒：getCabinetListAround(6 个中心点, scan_distance_km=3)
    ↓
按 location 名称锚定过滤（"中山大学(深圳校区)"）→ 48 台校园柜
    ↓
每台柜：new_chargeable vs 上一次 old_chargeable
    ↓
Δ = new - old
    ├── Δ < 0  →  新增 |Δ| 个占用，start_at = now，入队（basis='observed'）
    ├── Δ > 0  →  从队列头 FIFO 取 Δ 个，duration = now - start_at → charge_session
    └── Δ = 0  →  什么都不做，只更新 observed_at
    ↓
duration_stats()  →  median / p25 / p75（贝叶斯收缩到 180 分钟先验）
estimate_remaining()  →  remaining = max(0, 预计总时长 - 已过时长)
```

**它没有任何真值**。`chargeable` 只是"现在剩几个空位"，往下的一切都是推的。

关键设计取舍：

| 问题 | 处理方式 |
|---|---|
| 首次运行时柜子上已有人 | `occupied_now - known` 的缺口补成 `basis='backlog'` 的队列项，`elapsed` 只当**下界**、`remaining` 只当**上界**，且**不参与时长分布统计** |
| FIFO 假设不成立（后插先拔） | 无法检测，只能承认——这是系统性误差来源，写进 UI 说明 |
| 样本太少 | 贝叶斯收缩：`shrunk = (raw*n + 180*20) / (n + 20)`，n 小的时候被 180 分钟拉住 |
| 剩余时长为负 | `max(0, ...)` 截断 |
| 采集失败/漏采 | 只在 `previous.online == 1 and online == 1` 时才算差；有异常跳变时记 `failed` 而不写 session |

### 3.4 三者的能力边界对照（一张图）

```
                    逐桩位?    真实已充?   精确结束时刻?   需凭据?
汕大参考项目          ✅        ❌          ❌            ✅ 需签名凭据
青春号 TOSUN          ✅        ✅          ❌ 不展示      ✅ 需登录 token
本项目（无 token）     ❌        ❌ 推算      ❌ 推算       ❌ 全公开
本项目（有 token）     ✅        ✅ 固件 ct   ✅ 到秒        ✅ 用户本人 token
                                            ↑
                            这是本项目唯一但真实的增量：
                            平台有数据但不展示，我们把它算出来
```

**没有哪个方案"更好"**，它们服务不同需求：

- 汕大项目：用户想知道"3 号楼那台还有没有位置插"→ 需要逐桩位，愿意维护凭据
- 青春号：用户要下单 → 必须登录，一切都有，但它**不告诉你还要等多久**
- 本项目：用户想知道"现在出门去东教有没有位置 / 值不值得走一趟"→ 点位级 + 时间预期就够，且**不需要碰任何人账号**；
  愿意提供自己 token 的话，还能看到"这个桩还有 12 分钟空出来"

## 4. 同一个问题，三种答案

### 4.1 "东教学楼现在能充电吗？"

| 项目 | 回答 |
|---|---|
| 汕大参考项目 | 「东教学楼 A 设备：03 号空闲，07 号占用，11 号故障…」（若有对应设备清单） |
| 青春号 TOSUN | 「东教学楼，共 12 台柜，黄色气泡上写着 34」（点进去看每一格） |
| 本项目 | 「东教学楼：12 台柜 / 180 桩位 / **34 空闲**（18.9%）→ `mid`（一般）」 |

### 4.2 "我还要等多久才能插上？"

| 项目 | 回答 |
|---|---|
| 汕大参考项目 | **不回答**（没有时长数据） |
| 青春号 TOSUN | **不回答**（小程序里没有倒计时功能） |
| 本项目（无 token） | 「预计 30 分钟内会有 **3** 个位置空出；最快的一台约 **18 分钟**（基于 41 条历史记录，置信度 `medium`）」 |
| 本项目（有 token） | 「`CSTFN4004601` 端口 1：已充 268 分钟，目标 480 分钟（**概率 80%**），**04:22:15** 结束，还剩 212 分钟」<br>目标已确定时：「已充 7 小时 36 分，目标 8 小时，**01:18:35** 结束，还剩 24 分（**精确值**）」 |

> 这就是本项目存在的理由。前两者都**没有这个功能**——不是不肯做，是它们的定位不需要（汕大项目做"哪里有空位"，小程序做"我要下单"）。

### 4.2b "我就想去某一个区域，现在到底哪儿能插？"

| 项目 | 回答 |
|---|---|
| 汕大参考项目 | 按地点分组列出设备，但**不聚合成"该区域全部空闲桩位"清单** |
| 青春号 TOSUN | 地图气泡给一个柜的空闲**数字**，要自己点进每个柜逐格找空位 |
| 本项目 | **「区域空位查询」**：选一个区域 → 有空闲时按现场组号列出全部空闲桩号（"第 3 组 · CSTFL10643 · #5 #6 #9 号桩"）；**无空闲时**不写"满了"了事，而是从占用桩位里挑出**最快空出的 3–5 个**，逐个给出组号 / 物理桩号 / 已充时长 / 预计结束 / 还需多久，按剩余时间升序排列。 |

> 这个模块直接回答用户出门前的最终决策："去这个区域，具体插哪一格；如果全满，最快等多久、等哪个桩。"前两者都需要用户自己在多个柜之间来回切换比对。

### 4.2c "这个区域平时几点最挤？"

| 项目 | 回答 |
|---|---|
| 汕大参考项目 | 只有"当前"快照，**无任何历史趋势** |
| 青春号 TOSUN | 官方只给当下状态，**平台不提供任何历史查询接口** |
| 本项目 | **「每日桩位趋势」**：先选日期（最近 7 个自然日，默认折叠成一行「选择日期｜今天 ▾」）+ 选区域 + 选曲线（可用/占用），看**当天 0:00–23:59** 每 10 分钟一个采样点的折线。横轴是固定时间轴，当天没采完的部分留白（一眼看出采了多久）；右端橙点标最新值，图脚给日期 / 覆盖时段 / 均值。 |

> 这条曲线不是估算，而是本项目自己按 60 秒一轮采下来的历史（SQLite `cabinet_sample`）。
> 恰恰因为官方连历史都不给，"常驻采集 + 自己攒时间线"成了这类工具唯一能做出增量的地方——
> 也是本项目必须常驻运行、不能做成纯静态网页的根本原因。
> 它的价值随时间累加：跑得越久，日期栏里"有数据"的日子越多（当前上限 31 天）。

### 4.3 "数据准不准？"

| 项目 | 怎么保证 | 用户怎么知道 |
|---|---|---|
| 汕大参考项目 | 120 秒新鲜度窗口，超时排除出汇总 | 卡片上有"历史记录"标记 |
| 青春号 TOSUN | 平台直出，10 秒缓存 | 无需知道（它就是真相源） |
| 本项目（无 token） | 三级标注：`freshness.stale` / `confidence` / `basis` | UI 显示采集时间与"推算值"提示 |
| 本项目（有 token） | 固件 `ct` 真值 + 目标时长概率 + 硬上界 `480 − ct` | 橙色「实测」标签；精确值不带"至多/推断"字样，推断值带 `（推断 N%）` |

## 5. 踩过的坑（三项目对照）

| 坑 | 汕大参考项目 | 本项目 | 教训 |
|---|---|---|---|
| **凭据管理** | 必须从首页 JS 里正则挖 `app_id`/`app_secret`，只用内存不落盘、6 小时过期 | 公开模式无需凭据；可选模式由用户自己抓包提供本人 token，只存本机 `data/config.json`，只回后四位掩码 | 凭据型接口的维护成本高一个数量级 |
| **签名** | 必须算 `md5(sorted(k=v) + secret)`，错一个字符就 401 | 算法已逆出，但**平台不校验** | 逆出算法 ≠ 它有用；先测"不带签名能不能过"再决定投入 |
| **Body 编码** | POST 用 JSON（`separators=(",",":")` 不能带空格） | **必须 form**，JSON 直接 `code=1` | 猜编码是纯浪费时间——两种各试一次，30 秒解决 |
| **distance 单位** | 不涉及（用设备 id 不按坐标查） | **单位是 km 不是 m**，硬上限 100 条无分页，且**必须是整数**（传 `"3.0"` 会 `code=500`） | 参数名带 `_m` 是陷阱（本项目一度就这么写）；用"边界值探测"（1/2/50/2500）确定单位 |
| **UTF-8 编码** | 不涉及（无中文源码分析） | `gb18030` 解码让全部中文关键词归零（`充电` 从 67 次变 0 次） | Windows 环境读源码一律写死 `utf-8`，**不传 `errors`** |
| **location 空格** | 不涉及（按 id 索引） | 同一地点两个字符串（`西门右侧` / ` 西门右侧`） | 归并前先去空白比对 |
| **离群数据** | 按 id 白名单天然免疫 | 不按名称过滤会混入 52 条异地/测试柜 | 名称锚定 > 距离过滤 |
| **字段名陷阱** | 无（`state` 直接可用） | `chargeTime` 恒 `null`、`endTime` 恒等于 `updateTime`、`percentage` 恒 0 —— 三个"看起来最有用"的字段全废；真值在固件 `ct`/`cs` | **字段清单只能证明名字存在，不能证明有值**。必须逐字段实测取值再建模 |
| **假空闲** | `state` 不完整 → 灰 | `chargeable` 的语义不是「可充电数」而是「**红外没检测到东西且硬件正常**的端口数」（实测 `chargeable == count(infraed==0 AND status==1)`，48/48 吻合）。所以电池还插着的端口（充满未取/到点断电未取）**不在** `chargeable` 里，平台并没把它们当空闲 —— 只是不告诉你为什么不能用。实测这类 `blocked` 端口稳定 55~61 个 | 只看 `chargeable` 一个数字无法区分「空着」与「为什么不能用」。本项目拆成 `free`/`occupied`/`blocked`/`fault` 四类，四类之和恒等于 `capacity` 且 `free` 恒等于 `chargeable`（这是地图与明细永远一致的前提），并在**五处**同时暴露 `blocked`：概览另列「断电未取走 N 个」、点位卡片橙色计数、电柜组标签 `断电 N` 角标、桩位格虚线橙框「已断电」、详情显示 0.0V/0.000A。实现上固件采样范围必须含「平台判空闲但 `chargerStatus ∉ {0,1,7}`」的端口，且这类异常端口（约 50 个）**排在队列最前面**，第一轮就能全部发现 |
| **离线柜** | `state` 不完整 → 灰，排除出汇总 | `online=0` 的柜，桩位既不算空闲也不算占用 | 别强求 `free + busy + fault == physical_total`；离线要独立成档，不能显示成"已满" |
| **错峰采样** | 无状态，每次现查 | 60 秒一轮，时间线必须连续 | 漏采会让 FIFO 队列错位 |
| **地图落点** | 无地图（按固定 id 列表） | 微信 map 组件 + WGS84→GCJ02；**marker 本体钉真实坐标**，图标是平台图片（灰泡/彩泡/红泡，自带数字），仅**坐标完全相同**的柜才用 `processMapMarkers` 45° 放射散开 label | 本项目用 Leaflet + **三套可切换底图（`datum` 自适应）**复刻：`街道图 OSM/WGS84 → 高德图 GCJ02 → 卫星图 Esri/WGS84`，WGS84 底图直接用原始坐标、GCJ02 底图先转换；切底图时用 `gcj02ToWgs84` 反解视野中心避免跳动。**图标直接复用平台真实图片**（`web/vendor/markers/` 127 张，同 `getIcon` 逻辑：0 空位灰泡 `none0`、N 空位按柜型取 `cdz/cdg/hdg/qcz/gz`、离线红泡 `outLine0`）；不做任何人为像素散开，坐标相近的组沿路**自然叠放成斜排**（即小程序西园食堂区一排灰泡效果）；缩放由 Leaflet 重投影不漂移（icon anchor 恒 40px）。**口径实测**：原始坐标在 OSM 与 Esri 卫星影像上均精确落在西园6宿舍/农业银行楼群与路边停车带 → 平台坐标即 WGS84；**高德底图在本片区自带约 150–200m 偏移**，切到高德时地图注记显示橙色告警。自检：48 marker/0 破损、跨缩放锚点固定 40px、六点位街道图与卫星影像落位均已核验 |

## 6. 如果你也想做一个（选型建议）

按"你能拿到什么"倒推方案：

| 你的处境 | 选哪个方案 | 理由 |
|---|---|---|
| 平台有免登录的**逐桩位**接口 | 照抄汕大参考项目 | 真值链最完整，不需要推算 |
| 平台只有免登录的**汇总数** | 照抄本项目（无 token 模式） | 只能推算，必须做可信度标注 |
| 你有合法的**登录态** | 走本项目的有 token 模式 | 找**桩端固件**里的真计时器，不要信订单表里的时长字段（本平台那三个字段全是废的） |
| 你只有**网页截图** | 别做 | OCR 的延迟和错误率会让"实时"失去意义 |

**四条硬性建议：**

1. **先探边界，再写代码**。用 5 分钟测清楚：免登录能拿到什么、逐桩位要不要 token、`distance` 什么单位、硬上限多少条、form 还是 JSON。这四个问题的答案会决定整个架构。
2. **凡是推算的，必须标注**。`estimated: true` + `confidence` + `basis` + "非官方数据"文案，一个都不能省。用户看到"3 分钟后空出"去了一趟发现没有，如果没有标注过这是推算，那就是你的错。
3. **别伪装精细度**。只有电柜级数据就说"这台柜还有 2 个空位"，不要编造"3 号桩位空闲"。
4. **字段名 ≠ 字段有值**。本平台 `chargeTime` / `endTime` / `percentage` 三个看起来最有用的字段实测全是废的（`null` / 等于刷新时间 / 恒 0）。**拿到字段清单后必须逐字段实测取值**，否则整个模型建在沙上。真正有用的是没人会先去看的固件 `ct` / `cs`。

## 7. 一句话总结

**汕大参考项目证明了"数据够就能做到逐桩位"；青春号小程序证明了"官方有全部数据但不对第三方开放，也不告诉用户还要等多久"；本项目证明了"只有汇总数也能做出有时长预期的看板，而用户自愿提供凭证后，连平台没展示的固件计时器都能读出来，把结束时刻精确到秒——前提是诚实标注每一个数字的来源与可信度"。**
