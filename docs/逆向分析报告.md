## 1. 摘要

「青春号 TOSUN」是长盛泰富（川海）投放的换电/充电柜运营小程序，覆盖中山大学深圳校区等场地。腾讯 UniApp（Vue2）编译产物，主包 + 7 个分包，业务代码约 104 万字符。

**五条决定性的结论：**

1. **平台对未登录用户只公开"每台电柜的空闲数"**。【实测】`POST /v1/user/getCabinetListAround` 免登录可用，返回 17 个字段，其中真正表达"空位"的只有 `chargeable`（可充电数）与 `capacity`（总位数）。**没有逐桩位状态**。

2. **逐桩位的真实数据全部要登录，且无法伪造 token 绕过**。【实测】`checkCabinetInfo`、`getCaboxListByCabinetNo`、`queryAllBox`、`queryBoxInfo`、`get_charge_order_detail` 在无 token 时一律返回 `{"code":1,"msg":"登录状态已经失效,请重新登录"}`；用 `"1"` / `"test"` / UUID / 32 位 hex 四类伪造 token 系统复测，**全部失败**。其中 `getCaboxInfo` 特殊：`code=0` 但 `data` 是**所有字段为 `null` 的空壳**——字段清单可见，数值不可见。**但平台没有扫码/验证码登录入口**，只能微信授权手机号，所以第三方只能用"用户本人抓包提供的 token + mobile"这一条路（本项目即如此，见 §5.3）。

3. **「空闲数」与「充电时长」来自两个权限不同的接口**。免登录的 `getCabinetListAround` 只给电柜级汇总；逐桩位的 `caboxs[]`（含 `chargeOrderNo`/`chargerStatus`/`startTime`）全部锁在 `getCaboxListByCabinetNo` 后面，而**真正的计时器在桩端固件的 `queryBoxInfo` 里**（`ct` / `cs`）。这是整个项目的分水岭——参考项目 STU Charge Watch 只做空闲数，不是偷懒，而是公开接口只能给到这个粒度。

4. **🔴 用户选的目标时长藏在桩端固件的 `cs=6` 里**。【实测】桩自己计时、到点断电（`cs=6`），此时 `ct` **冻结在用户选择的目标值上**。全量扫描 12 个 `cs=6` 端口，`ct = [240, 480×11]`，**12/12 精确命中**小程序的时长档位；对照组 `cs=5`（手动停止）**0/9 命中**。因此「结束时刻 = `startTime` + 目标时长」可以**精确到秒**，「剩余 = 目标 − `ct`」是精确值。这是本次逆向最有价值的发现，也是本项目能做到"精确剩余时间"的唯一依据。

5. **小程序自身没有"剩余时长"这个功能**。【实测】全量源码检索 `倒计时`/`剩余时长`/`countdown`/`remainTime`/`leftTime`/`剩余分钟` 均**零命中**；唯一两处"剩余时间"出现在**套餐有效期**（`validDate`）的模板里，与充电无关。它对"时长"的处理只有两种：**下单时选一个预设时长**（`chargeHours`，不是已充时长），**订单结束后看两个静态分钟数**（`chargeChargeTime` / `chargeTakeTime`）。

因此第三方做"已充多久 / 还剩多久空出来"，**无 token 时**不可能从公开接口读到真实值，只能由自己累积时间线推算；**有 token 时**可以读到桩端真值并把结束时刻精确到秒（结论 4）。而「还剩多久转空闲」这一功能**小程序本身就没有**——它不是照搬，是本项目的原创增量。

**修正一个易误判的字段语义**：`chargeable` 不是「可充电数」，实测 48/48 精确吻合的公式是 `chargeable == count(infraed == 0 AND status == 1)`，即「红外未检测到物体（端口空着）且硬件正常」的端口数；`errorCell == count(status != 1)`。平台**没有**把「电池还插着」的端口算成空闲 —— 它只是不告诉你这些端口为什么不能用。本项目据此把端口分成 `free`/`occupied`/`blocked`/`fault` 四类，四类之和恒等于 `capacity` 且 `free` 恒等于平台 `chargeable`（§7.2.9）。

## 3. 包获取与解密方法

### 3.1 包落盘位置（【实测】）

微信 4.x（xwechat）把小程序包存在：

```
C:\Users\<user>\AppData\Roaming\Tencent\xwechat\radium\users\<用户hash>\applet\packages\<wxid>\<版本号>\*.wxapkg
```

本机该目录下共 **129 个 `.wxapkg`**（含其他小程序与插件）。目标小程序属于 3 个包：

| 文件名 | 大小 | 内容 |
|---|---|---|
| `__APP__.wxapkg` | 2 499 402 B | 主包（`app-service.js` / `app-wxss.js` / `app-config.json` 等） |
| `_pages_main_.wxapkg` | 483 722 B | `pages_main/` 分包（**充电业务核心**） |
| `_pages_setting_.wxapkg` | 471 267 B | `pages_setting/` 分包 |

> 3 个包的字节数之和远小于解包后总体积（5 978 713 B），因为它们只覆盖主包与两个分包；其余分包未下载到本机。**`pages_main` 必须拿到**——充电服务页面 `chargeService` 就在里面。

### 3.2 加密格式（【实测】）

微信 4.0+ 的 `.wxapkg` 前 6 字节是魔数 `V1MMWX`，之后是加密体：

```
偏移 0..5       "V1MMWX"（6 字节明文魔数）
偏移 6..1029    1024 字节 AES-256-CBC 密文
偏移 1030..     剩余字节，逐字节异或
```

### 3.3 解密算法（唯一可用解，【实测】已跑通）

```python
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC
from cryptography.hazmat.primitives import hashes

SALT = b"saltiest"
IV   = b"the iv: 16 bytes"

def key_for(wxid: str) -> bytes:
    kdf = PBKDF2HMAC(algorithm=hashes.SHA1(), length=32, salt=SALT, iterations=1000)
    return kdf.derive(wxid.encode())

def decrypt(wxid: str, data: bytes) -> bytes:
    key = key_for(wxid)
    dec = Cipher(algorithms.AES(key), modes.CBC(IV)).decryptor()
    head = dec.update(data[6:1030]) + dec.finalize()
    head = head[:1023]                       # 注意：取 1023，不是 1024
    xk = ord(wxid[-2]) if len(wxid) >= 2 else 0x66   # 密钥 = appid 倒数第二个字符的码位
    tail = bytes(b ^ xk for b in data[1030:])
    return head + tail                        # head(1023) + tail(剩余)
```

三个关键点，任一错都解不出合法包：

- **盐固定为 `saltiest`**，不是 appid 也不是设备信息
- **IV 固定为 `the iv: 16 bytes`**（字面 16 字节字符串，不是 hex）
- **异或密钥是 `ord(wxid[-2])`**，即 appid 的**倒数第二个字符**——对 `wx98d7c7d09b88b452` 就是 `'5'`，即 `0x35`

### 3.4 解包格式（【实测】）

解密后的明文是标准 wxapkg 结构，**没有**现成库能直接读（当时的 `wxappUnpacker` 对 V1MMWX 版本不适用），于是手工按二进制布局解析：

```
[0]        0xBE                    魔数
[1..4]     info1                   大端 uint32
[5..8]     indexInfoLength         大端 uint32
[9..12]    bodyInfoLength          大端 uint32
[13]       0xED                    魔数
[14..17]   fileCount               大端 uint32，文件条目数
[18..]     文件条目，共 fileCount 个，每个：
             nameLen   大端 uint32
             name      nameLen 字节，UTF-8
             fileOffset 大端 uint32（相对文件数据区起点）
             fileSize   大端 uint32
```

```python
import struct

def parse(raw: bytes) -> list[tuple[str, int, int]]:
    assert raw[0] == 0xBE, "不是合法 wxapkg"
    first, index_len, body_len = struct.unpack(">III", raw[1:13])
    assert raw[13] == 0xED, "索引区魔数不对"
    count = struct.unpack(">I", raw[14:18])[0]
    off, entries = 18, []
    for _ in range(count):
        name_len = struct.unpack(">I", raw[off:off + 4])[0]; off += 4
        name = raw[off:off + name_len].decode("utf-8");        off += name_len
        file_off, file_size = struct.unpack(">II", raw[off:off + 8]); off += 8
        if ".." in name:          # 防路径穿越
            continue
        entries.append((name, file_off, file_size))
    return entries
```

解包输出到本地临时目录 `_mp_src/wx98d7c7d09b88b452/`（该目录为反编译中间产物，不随仓库分发），共 5 978 713 B。核心文件：

| 文件 | 大小 | 作用 |
|---|---|---|
| `app-service.js` | 1 044 932 B（1 031 751 字符） | 全部 JS 业务逻辑（Vue 编译产物） |
| `app-wxss.js` | 668 223 B | 样式 |
| `app-config.json` | 31 812 B | 编译后的 `app.json`（pages / tabBar / subPackages / window） |

### 3.5 踩坑记录（这一节比算法本身更省时间）

#### 坑 1：网上流传的 AES key = `md5("0")` 是**旧版本**，对微信 4.x 完全无效

第一版解密脚本用的是：

```python
KEY = bytes.fromhex('cfcd208495d565ef66e7dff9f98764da')   # md5("0")
dec = Cipher(algorithms.AES(KEY), modes.CBC(KEY[:16]))
head = dec.update(body[:1024]) + rest ^ head[i % 1024]
```

失败表现：解密不报错，但**解出来的字节不是合法 wxapkg**（`raw[0] != 0xBE`、`raw[13] != 0xED`），后续解包拿到 0 个文件。

**教训**：网上教程大量互相抄，且都对应微信 3.x。判定"算法对不对"的唯一标准是**解密后第 0 字节是否等于 `0xBE`、第 13 字节是否等于 `0xED`**——不要看"有没有抛异常"。

#### 坑 2：`head` 取 1023 而不是 1024

`data[6:1030]` 是 1024 字节密文，AES 解密出来也是 1024 字节，但拼接时必须取 `head[:1023]`。

如果取 `[:1024]`，明文比正确值多 1 字节，后续所有 `fileOffset` 全部错位 1 字节，表现为：**解出的文件数量对，但每个文件内容开头少一个字符 / 整体乱码**。这个 bug 极难从"文件列表看着正常"中发现。

#### 坑 3：解析偏移用 `raw[1:9]` 会得到 0 个文件

正确是 `raw[1:13]`（3 个 uint32 = 12 字节），`fileCount` 在 `raw[14:18]`。曾有脚本把前两段当 `(info1, indexLen)` 各 4 字节解析后直接从 `raw[10:]` 读条目数，得到天文数字，随后循环里 `nameLen` 读越界。

**教训**：wxapkg 的索引区有**两个魔数**（`0xBE` 在头、`0xED` 在 `fileCount` 之前），两个都校验就能立刻定位偏移错。

#### 坑 4：`app-service.js` 是 UTF-8，用 `gb18030` 或 `errors="replace"` 会毁掉全部中文

这是本项目**代价最大**的一个坑。Windows 中文环境下，很多工具的默认编码是 GBK/ANSI，一旦用错，源码里的中文会变成"鍏呮弧"这类乱码，于是关键词全部搜不到，人会误以为"这个字符串在别的地方"。

量化对比（对同一份 `app-service.js` 原始字节分别解码）：

| 解码方式 | 解出字符数 | 替换符 `U+FFFD` | `充电` | `空闲` | `桩` | `青春号` | `柜电智能` |
|---|---|---|---|---|---|---|---|
| `utf-8` | 1 031 751 | **0** | **67** | 1 | **20** | **7** | **9** |
| `gb18030` | 1 035 304 | **556** | **0** | 0 | **0** | **0** | **0** |

**结论**：`gb18030` 下所有中文关键词计数归零。用 `errors="replace"` 更糟——它不报错，静默把无法解码的字节变成 `U+FFFD`，你会得到一份"能搜但什么都搜不到"的文件。

**因此本项目的所有读取一律写死 `encoding="utf-8"`，且不传 `errors` 参数**（让它在该报错时报错）。

#### 坑 5：PowerShell 5.1 读含中文的 UTF-8 文件会静默崩

`ConvertFrom-Json` 直接报 `传入的对象无效，应为“:”或“}”。(357)`。原因是 PS 5.1 的 `Get-Content`/`ConvertFrom-Json` 默认按 ANSI 解码 UTF-8 无 BOM 文件。**读接口返回的 JSON 样本请一律用 Python，不要用 PowerShell。**

连带教训：在 PowerShell 里用 `python -c "...含有 { } 和引号的长表达式..."` 极易触发 `字符串缺少终止符` / `数组缺少结束符` 的**外壳解析错误**（还没轮到 Python 就失败了）。**所有探测逻辑落地成 `.py` 文件再执行**，输出用 `> out.txt 2>&1` 落盘再读，避免 stderr 被 PowerShell 吞掉。

## 4. 请求签名还原

### 4.1 为什么要做

平台接口虽然**不校验**签名（见 4.4），但要理解"小程序是怎么调的"、以及在需要登录的场景下签名是否是必须的，就必须把混淆后的签名函数还原出来。这一步也为验证"我们的客户端行为与官方客户端一致"提供了依据。

### 4.2 混淆形态与还原路径（【实测】）

`app-service.js` 中请求核心函数（`0948` 模块的 `k`）被混淆成：

```js
o["content-type"] = "application/json";
"POST" == n.toUpperCase() && "form" === l &&
  (o["content-type"] = "application/x-www-form-urlencoded;charset=UTF-8");

o[g(327)] = Math.round(new Date / 1e3);   // timestamp（Unix 秒）
o[g(315)] = S();                          // nonceStr（UUID v4）

o[g("0x146")][g(334)](g(338))
  // 即 content-type.includes("application/x-www-form-urlencoded")
  //   → 把 params 全部写入待签串

k += g(316) + o[g("0x147")] + g(318) + o.nonceStr;
  // 即 "&timestamp=" + ts + "&nonceStr=" + nonce

var E = s.default.MD5(k).toString();
o[g("0x144")] = E;                        // signature

function S() {
  return "xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx".replace(/[xy]/g, function (e) {
    var t = 16 * Math.random() | 0;
    return ("x" == e ? t : 3 & t | 8).toString(16);
  });
}
```

`g(i)` 是一个**字符串表索引函数**，实现为 `g(i) => arr[i - 315]`（对十进制入参）与 `g("0xNNN")` 走十六进制分支。字符串表共 26 项，是 ROT16（每字符码位 +16）混淆后再由校验和自解的：

```js
["split", "content-type", "timestamp", "sort", "324099BDsjFg", "249780nTNyed",
 "134996jEUuFE", "16wIaStv", "lastIndexOf", "startsWith", "104350EFrRDk",
 "forEach", "length", "application/x-www-form-urlencoded", "713522jrYLVt",
 "18uWOSMG", "nonceStr", "×tamp=", "from", "&nonceStr=", "276TKwOEE", "set",
 "34342skiWHo", "1653555xJncFN", "keys", "signature"]
```

还原出的索引映射（关键几项）：

| 索引 | 明文 |
|---|---|
| `g(315)` | `nonceStr` |
| `g(316)` | `&timestamp=` |
| `g("0x144")` | `signature` |
| `g("0x147")` | `timestamp` |
| `g(318)` | `&nonceStr=` |

> 表中 `×tamp=` 是 `&timestamp=` 经 ROT16 后的残片（`&`→`×`、`t`→`…`），看到这种字符就知道混淆方式是"每字符 +16"。

### 4.3 最终算法（【实测】已实现并跑通）

```
1. 收集参数（业务参数 + timestamp + nonceStr）
2. 按 key 字典序升序排列
3. 逐项拼成 "k=v"，用 "&" 连接        → A
4. A += "&timestamp=<ts>&nonceStr=<nonce>"
5. signature = MD5(utf8(A)).hexdigest()   （小写）
6. 请求头带上 signature / timestamp / nonceStr / token
```

对应实现：

```python
import hashlib, time, uuid

def signature(params: dict, timestamp: int, nonce: str) -> str:
    pairs = [f"{k}={'' if v is None else v}" for k, v in sorted(params.items())]
    plain = "&".join(pairs)
    plain += f"&timestamp={timestamp}&nonceStr={nonce}"
    return hashlib.md5(plain.encode("utf-8")).hexdigest()

def _nonce() -> str:
    return str(uuid.uuid4())   # 足够等价于小程序的 UUIDv4 生成器
```

**注意一个易错点**：`timestamp` 与 `nonceStr` 在待签串里**也参与**（作为最后两段），但它们不进 `params` 的排序段。写错成"把 ts/nonce 也扔进 sorted"会得到错签名。

### 4.4 但平台并不校验它（【实测】）

关键实测：**完全不带 `signature` / `token` / `timestamp` / `nonceStr` 头，只发 `content-type` + form body，接口照样返回 `code=0`。**

同样地，把 `signature` 换成任意字符串 `"deadbeef"`、`token` 传空串，结果不变。

**结论与做法**：签名是平台"约定俗成"的装饰，不是安全边界。配套项目 `tosun_client.py` 仍然实现了正确的签名并带上（成本极低、行为与官方客户端一致、万一平台某天开始校验也不会突然挂），但**绝不依赖它**。

### 4.5 混淆里还有两坨无关的签名代码，别搞混

读码时会撞见另外两套"签名"实现，都**与本平台无关**：

1. **阿里云 HMAC-SHA256**：`HMAC-SHA256 Credential=... SignedHeaders=... AccessKey` —— 用于对象存储/短信等云服务
2. **腾讯云 serverless 签名工具**：`Ie = function(e, t) { var n = ""; return Object.keys(e).sort().forEach(...) }` —— 云函数调用签名

它们的共同特征是也出现 `Object.keys(...).sort()`，非常容易被误认为平台的待签串构造。**判别方法**：平台的待签串末尾一定要拼 `&timestamp=...&nonceStr=...`，而这两套都不拼。

## 5. API 全景

### 5.1 通用约定（【实测】）

| 项 | 规则 |
|---|---|
| 方法 | `POST` |
| Content-Type | **必须** `application/x-www-form-urlencoded;charset=UTF-8` |
| Body | **必须** form 编码（`urlencode`），**不能** JSON |
| 响应 | JSON，`code == 0` 为成功；`code == 1` 多为"登录状态已经失效" |
| 请求头 | 可带 `signature` / `timestamp` / `nonceStr` / `token`，**但服务端不校验** |

`code` 语义（【实测】，基于多次调用归纳）：

| `code` | `msg` | 含义 |
|---|---|---|
| `0` | 各接口自定义（如 `查询成功`） | 成功 |
| `1` | `getCabinetListAround error` | 参数缺失/非法（**不是**登录问题） |
| `1` | `登录状态已经失效,请重新登录` | 需要登录 token |

> 注意 `code=1` 有两种截然不同的含义，**必须看 `msg` 才能区分**。只判断 `code != 0` 会把"参数写错"误报成"需要登录"。

### 5.2 form vs JSON —— 实证（【实测】）

同一端点、同一参数，只改 body 编码：

| Body 形式 | 响应 |
|---|---|
| JSON（`{"longitude":113.9457,...}`） | `{"code":1,"msg":"getCabinetListAround error","data":null}` |
| form（`longitude=113.9457&latitude=...`） | `{"code":0,"msg":null,"data":[...]}` |

**这是本项目最省事也最坑的一个发现**：Spring 后端只认 `@RequestParam`，`@RequestBody` 没配。用 `requests.post(url, json=...)` 的人会在这里卡很久，且错误信息完全指向不了真实原因（它说"error"，不告诉你"编码不对"）。

配套项目的做法：

```python
body = urllib.parse.urlencode(clean).encode("utf-8")
headers = {"content-type": "application/x-www-form-urlencoded;charset=UTF-8", ...}
```

### 5.4 伪造 token 不可行（【实测】已系统证伪）

因为"逐桩位数据要登录"是本报告的核心约束，必须排除"其实构造个 token 就能过"这种可能。系统性复测：

| 伪造 `token` 取值 | 结果 |
|---|---|
| `"1"` | `code=1` `登录状态已经失效,请重新登录` |
| `"test"` | 同上 |
| 随机 UUID | 同上 |
| 32 位十六进制串 | 同上 |
| 空串 | 同上 |

对 `checkCabinetInfo`、`getCaboxListByCabinetNo`、`queryAllBox`、`queryBoxInfo`、`get_charge_order_detail` 逐一遍历，**全部失败**。

**结论：token 必须是真实登录态（服务端会话校验），无法构造。本项目不尝试绕过。**

### 5.5 「空闲桩位」与「充电时长」用的是两个不同接口 —— 全项目最重要的一句话

这是整份报告最需要记住的结构性事实：

| 能力 | 接口 | 免登录？ | 返回内容 |
|---|---|---|---|
| 空闲数汇总 | `POST /v1/user/getCabinetListAround` | ✅ **免登录** | `chargeable`（可充数）/ `capacity`（总数）/ `online` / `errorCell` |
| 逐桩位状态 | `POST /v1/user/checkCabinetInfo` | ❌ **需登录 token** | `caboxs[]`：每桩 `chargeOrderNo` / `chargerStatus` / `infraed` / `percentage` / `chargeTime` / `startTime` / `endTime` |

`checkCabinetInfo` 请求体（form）：`cabinetNo=<柜号>&mobile=<手机号>`。未登录返回 `{"code":1,"msg":"登录状态已经失效,请重新登录","data":null}`。

同一族接口在无 token 时一律失败：`checkCabinetInfo`、`getCaboxListByCabinetNo`、`queryAllBox`、`queryBoxInfo`、`get_charge_order_detail`。

**这个分界线的意义**：它解释了为什么参考项目 STU Charge Watch **只做空闲数**——不是偷懒，而是公开接口就只能给到这个粒度。也解释了为什么本项目要做"已充时长 / 剩余多久转空闲"，**只能靠汇总数的时间线推算**，无法从平台直接读取。任何把这个取舍含糊成"数据来自平台"的表述都是错的。

#### `distance` 单位是 km —— 最容易踩的语义坑（【实测】）

以校园中心 `(113.9457, 22.8036)` 为中心扫描：

北京坐标 `(116.397, 39.908)` 交叉验证：`distance=2500` → 100 条（最近 1826 km，说明 `2500` 被当成 2500 km）；`distance=50` → **0 条**。

**三条确定性结论：**

1. **`distance` 单位是公里**。传 `2500` 不是"2500 米"，而是 2500 公里（≈ 全球范围）。
2. **返回结果按 `distance` 升序排列**（实测：取回 100 条，`distance` 序列严格递增，首 5 项 `0.324/0.326/0.330/0.352/0.382`，末 5 项 `34.657/34.662/34.663/34.671/34.708`）。

> ⚠️ **命名陷阱（本项目源码里真实踩过）**：`tosun_client.list_around()` 的第二个形参最初叫 `distance_m`，但它直传平台的 `distance`，实际单位是 **km**；`data/sites.json` 里也曾写成 `scan_distance_m: 2500`（即 2500 km）。名字带 `_m` 纯属历史遗留，**不要**按米去理解或换算，否则会算出 2.5 km 的半径而漏掉数据。现已统一改名为 `distance_km` / `scan_distance_km`（默认 `3`，`/api/config` 里 clamp 到 0.5~50）。

### 5.8 `errorCell` 的语义：【推断】故障格数

**推理依据（全部【实测】）：**

1. 对 48 台校园柜逐条校验，`chargeable <= capacity` **全部成立**（0 例外）
2. `chargeable + errorCell <= capacity` 也**全部成立**（0 例外）
3. `errorCell` 在中大柜上的实际取值范围是 `0 ~ 10`
4. 换电柜（`cabinetType=1`）的 `errorCell` 恒为 0
5. **`errorCell` 在小程序全部 JS 中出现 0 次** —— 前端从未读取、从未使用、从未展示它

（2）是最有说服力的：如果 `errorCell` 是任意计数器，几乎不可能恒满足这个加法约束。它几乎只能是"总位数里被故障占掉的部分"。

（5）是**反面证据**，必须一起写出来：如果平台前端自己都不用这个字段，说明它要么是给后台/运维用的，要么是给别的客户端（App、公众号）用的——**没有前端代码可以交叉验证它的真实语义**。这进一步强化了"标为推断"的必要性。

**因此本项目按 `fault = errorCell` 使用，并在 `docs/API.md` 与 UI 中一律标注为"推断语义"。**

**平台自己的前端怎么看这件事（【实测】）**：小程序地图气泡数字是 `chargeable`，而**不是** `capacity - chargeable - errorCell`。也就是说平台没把故障格从"已占用"里摘出来给用户看；它只告诉你"现在有几根能用"。

| `port` | **物理桩位号** | 前端 `selectPort` 把 `port` 传给下单接口；也是 `queryBoxInfo` 的必传参数 |
| `chargeOrderNo` | 当前订单号 | **占用判定靠它前缀 `CD`** |
| `chargeTime` | 名义上是"已充时长" | 🔴 **实测对别人的订单恒为 `null` 或 `0.0`**（136 个占用端口：None 130、0.0 6、有意义 0 个）。真值在固件 `ct`（§7.2.8） |
| `startTime` / `endTime` | 订单起止时间 | `startTime` 是真实开始时刻（可用）；🔴 `endTime` 恒等于 `updateTime`（每次刷新时间），**不是充电结束时间**，不可用 |
| `infraed` | **红外占用信号**（`0`/`1`） | 前端渲染分支靠它；实测对占用端口恒为 `"1"`，无区分力 |
| `chargerStatus` | 充电器状态码 | 前端 `getChargerStatusText` 映射；占用判定需 `∈ {1,2,3}` |
| `status` | 桩位状态（`1` 正常等） | 前端渲染分支；实测恒 `"1"` |
| `percentage` | 电量百分比 | 前端 `percentage >= 80` 统计；🔴 实测**恒为 0**，不可用 |
| `voltage` / `ampere` | 电压/电流 | 前端 `calculateWatt` 求功率；固件 `vo`/`am` 更实时 |
| `boxTemp` / `chargerTemp` | 柜盒/充电器温度 | 安全告警用 |
| `door` | 柜门状态 | `opened_door` 相关判断 |
| `batteryNo` / `batteryType` | 电池编号/型号 | 换电业务 |
| `createBy` | 下单人手机号 | 🔴 **本项目直接丢弃，不入库、不进 API、不上前端** |

> **教训**：这份字段清单是从 `getCaboxInfo` 的未登录空壳反推的，只能证明**字段名存在**，
> 不能证明**字段有值**。真正可用的时间字段只有 `startTime`；`chargeTime` / `endTime` / `percentage`
> 三个"看起来最有用"的字段实测全是废的。这是先看字段名、后做实测差点踩进去的坑。

## 6. 数据模型

### 6.1 层级关系（【实测】）

```
运营商(source=CSTF)
  └── 电柜 cabinet        cabinetNo, cabinetType, capacity, chargeable, errorCell, online
        └── 桩位 port     由 capacity 表达数量（"10" → 10 个；"14,6" → 14 柜位 + 6 桩位）
              └── 柜盒 cabox   caboxId, port, chargeOrderNo, infraed, chargerStatus, chargeTime, ...
```

**层级只在"电柜 → 桩位数量"这一层对未登录用户可见。** 再往下（具体哪个桩位、什么状态、充了多久）全部锁在登录之后。

### 6.2 关键概念的精确定义

| 概念 | 平台字段 | 精确定义 |
|---|---|---|
| 电柜 | `cabinetNo` | 一台物理柜子。是接口返回的一条记录 |
| 总桩位数 | `capacity` | 字符串。混合柜 `"14,6"` 表示前 14 个柜位 + 后 6 个桩位，**总数 = 逗号分段求和** |
| 空闲桩位 | `chargeable` | 平台直接给出的"现在有几根能插" |
| 故障桩位 | `errorCell` | 【推断】异常/故障格数 |
| 已占用 | 计算值 | `capacity - chargeable - errorCell`（本项目口径） |
| 点位 | `location` | 中文地点名，如 `中山大学(深圳校区)医学园` |

### 6.4 必须过滤的离群数据（【实测】）

同一接口在 `distance=2500` 下会带回 52 条非校园记录，**必须过滤**，否则会严重污染统计：

| `cabinetNo` | `distance` | 问题 |
|---|---|---|
| `TEST0002` | 4.0 km | 测试柜 |
| `CSTF3000` | 24.8 km | 异地 |
| `GD10013` | 24.9 km | 异地 |
| `CSTF2000` | 25.1 km | `provinceCode = 北京市` |
| `CSTF2095` | 26.6 km | `location` 含「已拆除 暂存迈想」 |
| `CSTFN80001~80009`、`CSTFX50001~50010` | 35 km | 罗湖区 |
| `CSTFL10047` | — | `location` 为字符串 `"0"`，无地点名 |

配套项目的过滤口径（**双重**，缺一不可）：

```python
CAMPUS_MATCH = "中山大学(深圳校区)"
def is_campus(location):  return CAMPUS_MATCH in (location or "")   # 按名称锚定校园
# 外加 sites.json 的 scan_distance_km 控制扫描范围

只按距离过滤不够（`TEST0002` 只有 4 km，很近但不是校园柜）；只按名称过滤也不够（`CSTFL10047` 的 `location` 是 `"0"`，不含关键词所以会被正确排除，但如果它在校园内就会被漏掉）。**用名称做白名单锚定是最稳的口径**。

另有一台需要单独说明：`CSTFN40033`（东园食堂地下停车场）`location` 完全正常但 `online=0`。所以**不能用"offline 就是脏数据"来处理**——它是真实存在、只是当前离线的电柜，必须保留并在 UI 上标为离线。

## 7. 前端实现原理

### 7.1 空闲桩位查看 —— 平台是怎么做的

#### 7.1.1 数据获取：70 行代码里的三个决策（【实测】）

`app-service.js` 的 `11c6` 模块：

```js
getCabinets: function (e, n, r, o, a, c) {          // e=lng, n=lat, r=distance, o=batteryTypes, a=route, c=type
  var u = {
    longitude: e, latitude: n, distance: r,
    batteryTypes: o, type: c,
    mobile: getUser().mobile || "",
    source: appType
  };
  // localStorage 缓存 key: "cabinets" / "cabinets-expire"，TTL 10 秒
  //   setStorageSync(cabinetsExpireKey, now + 10)
  // 命中未过期缓存就直接返回，否则：
  return request(api.getCabinetListAround, u, "POST", {}, null, a);
}
```

**决策 1：缓存 10 秒。** 不是 60 秒，不是不缓存。说明平台预期"拖动地图时会连续触发查询"，用 10 秒窗口吃掉抖动。

**决策 2：`distance` 传 `50`。** 调用点：

```js
switchType: function (e) {
  ... getCabinets(locationNow.longitude, locationNow.latitude, 50, batteryTypes, "pages/index/index", e) ...
}
```

传 **50** 即 50 km。这解释了为什么在小程序里定位稍偏一点就能看到几十公里外的柜——**它本来就是广域查询**。配合 §5.6 的"硬上限 100 条 + 按距离升序"，平台实际拿到的永远是"离我最近的 100 台"。

**决策 3：`routeGuard` 中断机制。** `request(url, params, method, header, timeoutFlag, routeGuard)` 内部有：

```js
setInterval(1000, function () {
  if (当前页面 route !== routeGuard) abort();   // "任务中断"
});
```

即：**查询发出后页面被切走，就主动 abort**。这是很务实的移动端做法（用户滑走了就没必要耗流量），但也意味着"快速切页会丢结果"。

**其它渲染细节（【实测】）：**

- **坐标系转换**：`getMarkers` 里做 WGS84→GCJ02，`transformFromWGSToGCJ(s.latitude, s.longitude)`。平台上报的是 WGS84，微信地图要 GCJ02，不做转换会偏移几百米

  > 但需注意：**高德瓦片本身在光明区公常路一带自带约 150–200m 系统性偏移**，同一坐标在 OSM/卫星图上落在宿舍楼群、在高德图上却落到校外商铺（如「雅迪电动车纯银车行」）。因此判断落点是否准确**不能只用高德底图**，必须用 OSM 或卫星影像这类 WGS84 实测底图交叉验证。

- **电池型号不匹配时置 0**：`batteryTypes.includes(e)` 为假 → `p.content = 0`、`p.iconPath = baseIconPath + "0"`；且 `content == 0 && baseIconPath !== "outLine"` → 换成 `none0` 图标、`zIndex = 1`
- **分类 tab 状态叠加**：`cabinetType=1` 时 `path` 还叠加 `6 == cabinetStatus ? "gz" : "hdg"`（故障/正常两种图标）

#### 7.1.3 点开电柜 → 逐桩位抽屉（`cabinet-panel` 组件）

`chunk_3.appservice.js` 中的 `components/cabinet-panel/index`（`app-service.js:2614` 附近）。

**两个核心判定函数（【实测】原文）：**

```js
isCaboxOccupied: function (n) {
  return !(!n.chargeOrderNo || "CD" != n.chargeOrderNo.substring(0, 2));
},
getChargerStatusText: function (n) {
  return 1 == n || 3 == n ? "充电中"
       : 0 == n || 7 == n ? "待机"
       : 2 == n ? "预充"
       : 5 == n ? "充电停止"
       : 6 == n ? "未充满"
       : "";
}
```

**占用判定 = 订单号前两位是 `CD`。** 这是整个"空闲桩位查看"最本质的实现：平台不去读某种 `occupied` 布尔字段，而是**看这个柜盒有没有挂着有效充电订单**。`CD` 应是 `Charge` 的订单前缀（同库里还有换电订单，前缀不同）。

**桩位状态文案映射（`chargerStatus`）：**

| 码 | 文案 |
|---|---|
| `0` / `7` | 待机 |
| `1` / `3` | 充电中 |
| `2` | 预充 |
| `5` | 充电停止 |
| `6` | 未充满 |
| 其它 | `""`（空串） |

注意 `1` 和 `3` 都映射为"充电中"、`0` 和 `7` 都映射为"待机"——**一个状态位被复用了两种含义**，说明 `chargerStatus` 可能是多段编码或兼容了不同硬件代次。

**渲染时的条件分支（`app-service.js` + `page-frame.js` 交叉验证，【实测】）：**

```js
$mp.data = Object.assign({}, {$root: {
  g0: caboxs.length,
  g1: caboxs.length,
  l0: caboxs.length > 0
      ? __map(caboxs, function (t, e) {
          return {
            $orig: __get_orig(t),
            m0: 1 == t.infraed ? isCaboxOccupied(t) : null,   // ← 关键
            m1: getChargerStatusText(t.chargerStatus)
          };
        })
      : null
}});
```

**`m0`（是否占用）只在 `infraed == 1` 时才计算。** `infraed` 是**红外占用信号**（infrared detected）。也就是说平台有两条独立的占用证据源：

1. **红外检测**（`infraed`）：物理层探测到有东西插着
2. **订单号**（`chargeOrderNo` 前缀 `CD`）：业务层有活跃订单

渲染分支（`page-frame.js` 模板表达式）：

| 条件 | 界面表现 |
|---|---|
| `infraed == 1 && status == 1` | 橙色「被占用」 |
| `infraed == 0 && status == 1` | 「可使用」 |
| 其它（`status != 1`） | 红色「故障」 |

**这个设计对第三方是致命的**：红外信号与订单号都在 `cabox` 实体里，而这个实体需要登录。所以**未登录用户永远拿不到"哪一个桩位空着"**，只能拿到"这台柜还有几个空位"。

### 7.2 充电时长 —— 平台是怎么做的

#### 7.2.1 下单时：预设时长列表，`"充满"` 按 8 小时计费

`pages_main/chargeService`（`pages_main/chunk_3.appservice.js:369`，等价内容见 `pages_main/app-service.js:565` 附近）。

**`data` 里的时长相关字段（【实测】原文）：**

```js

**金额计算（【实测】原文）：**

```js

**这里是本项目最值得写进报告的一处设计：选「充满」时，前端按 8 小时预估计费。**

- 若 `preChargingFlag == "1"`（预充模式），用服务端下发的 `maxAdvanceAmount` 作为封顶金额
- 否则直接 `8 * chargePerHour`

也就是说**平台自己也不知道"充满"要多久，它用 8 小时当上限来收预付款**。这与 `timeList` 最大项就是 `8` 完全一致。

**提交时（【实测】原文）：**

```js

d.chargeTime = "充满" == c.chargeHours ? 8 : c.chargeHours;

**`"充满"` 在请求里被替换成数字 `8`。** 平台服务端根本不认识"充满"，它只认识小时数——"充满"纯粹是前端的一个别名。这把"充满 = 8 小时"从"计费巧合"坐实为"协议事实"。

#### 7.2.7 三个「时长」概念必须分清（最容易写错的地方）

读码时最危险的一件事是把三个不同的东西当成同一个"充电时长"。它们字面相近、出现位置相近，含义完全不同：

| 名称 | 出处 | 到底是什么 | 谁能拿到 |
|---|---|---|---|
| `chargeHours` | `chargeService` 页 `data`，值域 `["充满", 0.5, 1, …, 8]` | **用户下单时*选择*的时长**。是一个订单*参数*，不是已充时长 | 公开（前端硬编码 + 提交到下单接口） |
| `cabox.chargeTime` | 逐桩位实体（`getCaboxInfo` / `checkCabinetInfo` 的 `caboxs[]`） | **该桩位已充的分钟数**，服务端置值 | ❌ 需登录 |
| `chargeOrderDetail.chargeChargeTime` | 订单详情（`get_charge_order_detail`） | **这一单最终充了多久（分钟）**，订单结束后才有 | ❌ 需登录 |

**特别强调 `chargeHours` 不是"已充时长"。** 它是下拉框里选中的那个数字，选中时前端立刻用 `computeMoney` 算出预付款——从头到尾不随时间推进而增长。如果把 `chargeHours` 当成"用户已经充了几小时"写进文档或代码，整个语义就崩了。

配套的第四个概念：

| 名称 | 出处 | 含义 |
|---|---|---|
| `chargeOrderDetail.chargeTakeTime` | 订单详情 | **占用时长（分钟）**——从插上到拔走的整段时间，包含"充满后没及时拔"的空占 |

`chargeChargeTime` 与 `chargeTakeTime` 是两个数，因为计费是两档（充电 1.5 元/时、占用 0.25 元/时，见 `rent/rent` 页话术）。

#### 7.2.8 🔴 关键发现：目标时长藏在桩端固件的 `cs=6` 里

这是本次逆向最有价值的一条结论，也是「精确算剩余时间」的唯一依据。

**桩是独立计时的**：`startUseChargePile` 把 `chargeTime`（小时）发给平台，平台再下发给桩，
桩自己计时、到点断电，**不依赖平台在线**。所以计时器的真值在桩上，不在平台的订单表里。

**桩端固件接口**：`POST /v1/user/queryBoxInfo`（**必带 `port`**，不带 `port` 返回 `data={}`）。
返回 `data.box[]`，每个 box 的字段（大小写双份）：

| 字段 | 含义 | 实测值 |
|---|---|---|
| `ct` / `CT` | **已充电分钟数** | 与 `now − startTime` 中位偏差 2.5 分钟 |
| `cs` / `CS` | **桩端状态码** | 见下表 |
| `vo` | 电压 | 充电中 220.0V；已断电 0.0V |
| `am` | 电流 | 充电中 ~0.8A；已断电 ~0.006A |
| `eg` | 已充电量 | — |
| `po` | 端口号 | — |
| `im` | 未知 | **恒为 `000000000000000`**，与目标时长无关（已排除） |

**`cs` 码表（实测推导，平台无文档）**：

| `cs` | 含义 | 电压/电流实测 | 与平台 `chargerStatus` 关系 |
|---|---|---|---|
| `0` | 已断电（空闲/陈旧） | 0.0V / 0.006A | `0` 或 `7` |
| `1`/`2` | 预充 | — | `1`/`2` |
| `3` | **充电中** | 220.0V / 0.812A | `3` |
| `5` | 用户手动停止 | 0.0V | `5` |
| `6` | **到点断电（充满/到目标）** | 0.0V | `6` |
| `8` | 故障 | — | `8` |
| `10` | 离线 | — | — |

**决定性证据：`cs=6` 时 `ct` 冻结在用户选择的目标时长上。**

2026-11-19 全量扫描（48 柜 / 624 端口 / 采样 507 个）中：

| 分组 | 数量 | `ct` 值 | 命中 `timeList` 档位（`30/60/120/180/240/300/360/420/480`） |
|---|---|---|---|
| `cs=6` | 12 | `[240, 480, 480, 480, 480, 480, 480, 480, 480, 480, 480, 480]` | **12/12 = 100%** |
| `cs=5`（手动停止） | 9 | `[87, 1, 141, 272, 476, 11, 33, 218, 165]` | **0/9 = 0%** |
| `cs=3`（充电中） | 361 | 连续分布，max 476 | 仅 15% 落在 ±5min 内（符合预期） |
| `cs=0`（陈旧订单） | 15 | 全 0，或 `startTime` 在 2023/2024 年 | 不适用 |

对照组 `cs=5` 的 0/9 命中是**最关键的排除实验**：如果 `ct` 只是"随手一个数"，`cs=6` 不可能 12/12 精确落在档位上。
**所以 `cs=6` 的 `ct` 就是用户当初选的目标时长（分钟）。**

**由此得到的精确公式：**

```
目标时长 = cs==6 ? ct : 由档位分布反推
结束时刻 = startTime + 目标时长              ← 精确到秒
剩余时长 = 目标时长 − ct                     ← 精确值
```

**目标不确定时的硬上界**：`ct ≥ 420` 时只剩 `480` 一个档位可选 → `slot_constraint` 精确；
其余情况给「至多 `480 − ct` 分钟」，因为平台最长 480 分钟，实测 364 个充电中端口 `ct` 最大 476，无一超 480。

> 实测样例：`CSTFN4004601` 端口 1，开始 `20:22:15`，已充 268 分钟，
> 目标 480 分钟（概率 80%）→ 预计 **04:22:15** 结束，还剩 212 分钟。

#### 7.2.9 端口四分类：`chargeable` 到底是什么意思

这一节记录一个**容易误判的字段语义**，以及由此推出的分类口径。

**误判与纠正**。早期我根据小程序代码把 `cabox.chargeOrderNo` 以 `CD` 开头 **且** `chargerStatus ∈ {1,2,3}` 当作占用判定，
其余算空闲。这样算出来的空闲数比平台 `chargeable` **多出约 60 个**（同一时刻 `chargeable=374` vs 我推出的空闲 `436`）。
我最初以为这是「平台 bug：`cs=6` 到点断电的端口被当成空闲」，但逐柜穷举验证后推翻了：

**决定性公式**（48 台电柜逐柜比对，**48/48 精确吻合**，三个不同中心点、连续三轮复测稳定 47~48/48）：

```
chargeable == count(infraed == 0 AND status == 1)
errorCell  == count(status != 1)
```

即 `chargeable` 的语义是「**红外没检测到东西（端口空着）且硬件正常**的端口数」，
**不是**「没在充电的端口数」。`infraed` 是字符串 `'0'/'1'`，`status` 实测只有 `{1: 544, 3: 80}` 两个取值。

**关键佐证**：`chargerStatus=6`（到点断电）的 29 个端口 `infraed` **全为 1** ——
平台本来就没把它们算进 `chargeable`。所以平台**没有**把「电池还插着」的端口当空闲展示；
它只是不告诉你这些端口为什么不能用。

**由此定下的四分类**（同时满足 `free == chargeable` 且四类之和 `== capacity`，48/48 成立）：

| 分类 | 判定 | 含义 |
|---|---|---|
| `free` | `status==1 且 infraed==0` | 真的空着，插进去就能充 |
| `occupied` | `infraed==1 且 chargerStatus ∈ {1,2,3}` | 别人正在充 |
| `blocked` | `infraed==1` 但未充电 | 电池还插在柜里（充满未取 / 到点断电未取），插不进去 |
| `fault` | `status != 1` | 硬件异常 |

实测全量分布：`free=368 / occupied=115 / blocked=61 / fault=80`，合计 624。

**边界情况**：有 5 个端口 `chargerStatus=3` 但 `infraed=0`、`chargeOrderNo` 为字符串 `'None'`。
平台按 `infraed` 判，把它们算进了 `chargeable`。为保持同步，本项目也必须算 `free` ——
这类「平台说空但固件说在充」的少数派，以平台的 `chargeable` 为准，否则地图与明细永远对不上。

**`blocked` 的五层呈现**（这是平台不给、小程序也不展示的一类，实测稳定 55~61 个端口）：

| 层级 | 呈现 |
|---|---|
| 全场概览 | 「空闲桩位」= 平台 `chargeable`（与小程序地图一致），另起「断电未取走 N 个」 |
| 点位卡片 | 「断电未取走 N 个」（橙色加粗） |
| 电柜组标签 | `断电 N` 角标 |
| 桩位网格 | 虚线橙框 + 「已断电」字样（区别于实心橙「被占用」） |
| 桩位详情 | 「已断电未取走」+ 目标时长 + 剩余「即将空出」+ 0.0V/0.000A |

`_schedule_box_sampling` 的采样范围必须包含「平台判空闲但 `chargerStatus ∉ {0,1,7}`」的端口，
否则永远发现不了 `blocked`。实测 `chargerStatus ∈ {5,6,8,10}` 的端口约 50 个，
数量远小于全部待采端口，因此实现上把它们**排在采样队列最前面**，
保证第一轮（约 2 分钟）就能全部发现，用户不必等几轮轮转。

**一致性校验**（这是「地图与点位明细数字永远一致」的前提，每次改口径都要重跑）：
- `free + occupied + blocked + fault == capacity`，48 台全部成立；
- 明细里 `state=='free'` 的端口数 `== chargeable`，48 台全部成立。

#### 7.2.10 「还剩多久转空闲」是本项目的原创增量

必须把这句话说清楚，避免读者误以为本项目照搬了小程序：

**小程序本身没有"还剩多久转空闲"这个功能。** 用户能看到的只有：

- 状态文案（`"正在充电中..."`）
- 瞬时功率（`voltage × ampere`）
- 电量百分比（`cabox.percentage`）
- 自己下单时选的那个预设时长

充电过程中，**没有任何界面告诉用户"还要多久"**；看板外部的人就更不可能知道"这台柜子什么时候会空出来"。

这也是本项目真正多出来的那部分，分两条链路：

| 链路 | 依据 | 精度 |
|---|---|---|
| A：时间线推算（`tracker.py`，无 token） | `chargeable` 的变化顺序 + 历史样本条件生存估计 | 推算，带 `confidence` |
| B：固件精确计算（`box_sampler.py` + `target_model.py`，有 token） | 桩端 `ct` + `startTime` + 目标时长反推 | 目标确定时**精确到秒** |

两条链路都用 `basis` / `elapsed_is_lower_bound` / `remaining_is_upper_bound` / `confidence` /
`target_probability` 如实标注可信度。**链路 A 是推算；链路 B 的 `ct` 与结束时刻是桩端真值。**

## 8. 我们与它的能力差异

完整三列对比见 [`实现原理对比.md`](实现原理对比.md)。这里只讲**由逆向结论直接导出的三条硬约束**。

### 8.1 约束一：未登录拿不到逐桩位状态

平台的逐桩位数据需要登录（§5.3、§5.5）。任何声称"未登录拿到逐桩位"的方案，要么是登了别人的号，要么是把电柜级汇总数伪装成桩位级。

**本项目的应对**：分两种模式。

- **公开模式（默认，无 token）**：不伪造物理桩位。用 `chargeable` 的变化顺序构造**逻辑桩位**，并在每个响应里显式带：

```json
"note": "桩位号为逻辑编号，按空闲数变化顺序推定，非真实物理编号"
```

  以及每个桩位的 `basis` 取值 `observed` / `backlog` / `derived`，让 UI 能区分"真看见的"与"推的"。

- **凭证模式（用户自己提供 token + mobile）**：直接调 `getCaboxListByCabinetNo` 拿到**真实物理桩位号**与
  `startTime` / `chargerStatus` / `chargeOrderNo`，`note` 不再出现，`basis` 变为固件真值来源
  （`firmware_ct` / `firmware_frozen` / `slot_constraint`）。本项目**不伪造登录**，token 必须由用户
  在微信里登录一次后自行抓包提供（见 [`抓包获取Token指南.md`](抓包获取Token指南.md)）。

### 8.2 约束二：真实充电时长可以拿到（固件），但目标时长要靠反推

**早期结论（已修正）**：曾认为未登录视角下唯一可得的时间信息是"`chargeable` 在什么时候变了"。
**实测推翻**：提供 token + mobile 后，`queryBoxInfo` 直接暴露桩端固件计时器，`ct` 就是**精确已充分钟数**。

| 数据 | 来源 | 精度 |
|---|---|---|
| 开始时刻 | `getCaboxListByCabinetNo` 的 `startTime` | 精确到秒 |
| 已充时长 | `queryBoxInfo` 的 `ct` | 精确（与 `now − startTime` 中位偏差 2.5 分钟） |
| 目标时长 | 无接口直接给；`cs=6` 时 `ct` 冻结在目标值上 | `cs=6` 精确；`ct ≥ 420` 由档位约束精确；其余靠分布推断 |
| 结束时刻 | `startTime + 目标时长` | 目标精确时精确到秒 |

**本项目的应对**：三条链路并存，按数据可得性自动降级（`tracker.py` → `box_sampler.py` → `target_model.py`）。

公开模式（无 token）仍只有 `chargeable` 时间线，这套推理有**两个必须诚实说明的失真源**（这决定了 UI 必须标注"推算"）：

1. **FIFO 是假设不是事实**：`chargeable` 上升时，我们不知道是哪个桩位空了，只能按先入先出取队头。若实际是"后插的先拔"，记录到的时长会偏长。
2. **起点下界问题**：程序首次运行时，所有柜位上已经有人。这些占用的真实起点未知，我们只知道"至少从我们开始观察时就已经占着"。这类事件被标 `basis = "backlog"`，其 `elapsed` 只能当**下界**、`remaining` 只能当**上界**，且**不参与时长分布统计**（否则会把分布拖向自己运行的那几个小时）。

凭证模式（有 token + mobile）下，上面两个失真源**全部消失**：`startTime` 给精确起点、`ct` 给精确已充，
不需要 FIFO 假设也不需要 backlog 补位。剩余的失真源只剩一个：**目标时长推断可能错**，
以及用户随时可能手动结束（`cs=5`，实测占 3.7%）。

### 8.3 约束三：不能用平台的配色语义

平台地图颜色编码的是**类型**（蓝=换电柜、绿=充电柜、黄=充电桩、紫=汽车桩），不是忙闲（§7.1.2）。而本项目要看板"哪儿有空位"，必须编码**空闲率**。

**本项目的应对**：空闲率四档 + 离线一档（`none/low/mid/high/offline`），空闲率阈值 `0 / 15% / 40%`，`offline` 由 `online` 字段独立判定、不参与空闲率分级。为什么不是照抄参考项目的三档 25%：实测本校区各点位空闲率跨度是 0% ~ 90%，三档 25% 会让"15%"和"40%"落进同一档，失去区分度。为什么 `offline` 必须独立成档：`none` 的意思是"柜子在线、确实一个空位都没有"，`offline` 的意思是"这台柜子失联、我们什么都不知道"，把后者显示成"已满"会让人白跑一趟（§6.3）。

## 9. 合规与边界

### 9.1 我们做了什么

| 行为 | 说明 |
|---|---|
| 只调用 1 个公开接口做主数据 | `getCabinetListAround`（免登录） |
| 调用 2 个公开接口做增强 | `getCabinetInfoByCabinetNo`（电柜档案）、`getChargePerHour`（定价）；**失败即降级，不阻塞** |
| 可选：用户**自己提供**凭证后读逐桩位与固件 | `getCaboxListByCabinetNo`、`queryBoxInfo`；token 只存本机 `data/config.json`，只做只读查询，API 响应只回后四位掩码 |
| 读取本机已安装的小程序包 | 用于理解接口语义与字段含义；产物不入库、不再分发 |

### 9.2 我们明确没做什么

| 未做 | 原因 |
|---|---|
| 伪造登录 / 抓取他人 token | 只用使用者**本人**在微信里登录后自行抓包得到的凭证；不实现任何登录绕过 |
| 调用任何订单/支付/启停接口 | 本项目只读（`start_use_charge_*` / `operate/end_charge_order` 等一律不调） |
| 反向工程平台服务端 | 无必要 |
| 高频轮询 | 采集间隔 60 秒，与平台自身缓存（10 秒）和小程序刷新节奏同量级；固件采样每轮 180 端口、双 TTL（110 秒重采 / 900 秒可读）、轮转游标、异常端口优先 |
| 分发解包产物或密钥材料 | 报告只描述方法，不附带原始包体 |
| 展示任何用户个人信息 | 接口返回的 `mobile` / `createBy` 字段被**完全丢弃**，不进数据库、不进 API、不进 UI |

### 9.3 关于签名的定位

平台不校验签名（§4.4）这一事实，**不构成**"可以随意调用"的授权。本项目的边界来自两点自我约束：

1. **只读**：不发任何会改变平台状态（订单、充电、柜门）的请求
2. **低频**：60 秒一次、单次最多 6 个中心点并发，与官方客户端的行为同量级

### 9.4 免责声明的强制要求

`docs/API.md` §7 定义的文案必须在 UI 首页可见，且 `GET /api/meta` 的 `disclaimer` 字段必须原样返回：

> 本页面数据来自青春号 TOSUN 公开的附近电柜查询接口（`getCabinetListAround`），仅做只读聚合与展示，不涉及登录、账户、支付、订单或启停充电。"已充时长 / 剩余时长"为基于空闲数变化的历史推算，**非平台官方数据**，仅供参考。

### 10.1 只验证接口（不需要解包，最快）

```python
# 保存为 probe.py，用 python probe.py 运行（不要在 PowerShell 里用 python -c 拼长串）
import json, urllib.parse, urllib.request

BASE = "https://cloud.tosunelectric.com"
EP = "/v1/user/getCabinetListAround"

params = {
    "longitude": 113.9457, "latitude": 22.8036,
    "distance": 2,                  # 单位 km！
    "batteryTypes": "", "mobile": "", "source": "CSTF",
}
body = urllib.parse.urlencode(params).encode("utf-8")
req = urllib.request.Request(
    BASE + EP, data=body, method="POST",
    headers={
        # 这两行是关键：form 编码；JSON body 会得到 code=1
        "content-type": "application/x-www-form-urlencoded;charset=UTF-8",
        "accept": "application/json",
    },
)
with urllib.request.urlopen(req, timeout=20) as r:
    payload = json.loads(r.read().decode("utf-8", "replace"))

print("code =", payload.get("code"))
data = payload.get("data") or []
print("返回条数 =", len(data))
campus = [x for x in data if "中山大学(深圳校区)" in (x.get("location") or "")]
print("校园柜 =", len(campus))
print("总位数 =", sum(sum(int(float(s)) for s in str(x["capacity"]).split(",") if s.strip()) for x in campus))
print("空闲数 =", sum(int(x["chargeable"]) for x in campus))
```
